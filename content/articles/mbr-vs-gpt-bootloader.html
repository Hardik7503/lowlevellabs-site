Start with the basic idea

A disk does not know about files or partitions. It stores numbered blocks called sectors, traditionally 512 bytes each, addressed by a Logical Block Address (LBA): sector 0, sector 1, sector 2, and so on up to the end of the disk.

A partition is a contiguous range of sectors set aside for one purpose, such as "sectors 2048 to 1,050,623 hold the Windows C: drive". The partition table is the list of those ranges, written at a known place at the start of the disk so every operating system and firmware can find it.

Don't mix up the layers

MBR and GPT are partition table formats (how the disk is divided). BIOS and UEFI are firmware (what runs at power-on). They are often paired, BIOS with MBR and UEFI with GPT, but they are different things. See BIOS vs UEFI.

MBR: everything in one sector

The Master Boot Record occupies exactly one sector, LBA 0. Into those 512 bytes it packs three things:

The 2 TiB limit, worked out

The start and size fields are 32-bit numbers counting sectors. The largest value is 232 ≈ 4.29 billion sectors. Multiply by 512 bytes per sector: 232 × 512 = 241 bytes = 2 TiB. Space beyond that simply cannot be described. Disks with 4096-byte sectors push the limit to 16 TiB, but that does not help 512-byte-sector disks.

The four-partition limit

There is room for only four entries. To get more, one entry can be an extended partition containing a linked list of "logical" partitions. It works, but it is a workaround, and the chain is fragile.

How BIOS boots from MBR

  1. BIOS loads LBA 0 to memory address 0x7C00, checks for 55 AA, and jumps to the first byte.
  2. 446 bytes is not enough for a real bootloader, so this code is just stage 1: it loads a bigger stage from elsewhere on the disk.
  3. Classic DOS/Windows MBR code finds the partition marked active (0x80) and runs its first sector. GRUB instead loads its core image from the gap between the MBR and the first partition (sectors 1 to 2047 on modern layouts).
  4. The later stage understands filesystems, reads its configuration and loads the kernel.

GPT: a proper data structure

The GUID Partition Table is part of the UEFI specification. It fixes MBR's limits by using 64-bit sector addresses, keeping 128 entries by default, and storing everything twice with checksums.

  • Protective MBR at LBA 0: a fake MBR with one partition of type 0xEE covering the whole disk. Old tools see a disk that is "full" and leave it alone instead of offering to format it.
  • Header at LBA 1: disk GUID, where the entry array is, how many entries, and CRC32 checksums of itself and of the entries.
  • Entries: each holds a type GUID (what kind of partition, for example C12A7328-F81F-11D2-BA4B-00A0C93EC93B for an ESP), a unique partition GUID, 64-bit first and last LBA, attribute flags and a name.
  • Backup copies of the header and entries at the end of the disk.

How UEFI boots from GPT

UEFI does not execute anything from LBA 0. It reads the GPT, finds the partition whose type GUID says "EFI System Partition", mounts its FAT filesystem, and runs the .efi file named in its boot entry. The disk's first sector is irrelevant to a UEFI boot.

Mixed combinations

  • BIOS + GPT works with GRUB: you add a tiny "BIOS boot partition" (about 1 MB, no filesystem) where GRUB stores its core image, because GPT has no gap after LBA 0 to hide it in.
  • UEFI + MBR is allowed by the specification if the disk has an ESP (type 0xEF), but Windows refuses to install that way.

Look at your own disk

```bash sudo fdisk -l /dev/sda # "Disklabel type: gpt" or "dos" (= MBR) sudo gdisk -l /dev/nvme0n1 # GPT details, checks header CRCs sudo dd if=/dev/sda bs=512 count=1 | xxd | tail -n 2 # see 55 aa at the end of LBA 0 ```
Key takeaway

MBR is one 512-byte sector with boot code, four 32-bit partition entries and a signature, which limits disks to 2 TiB. GPT uses 64-bit addresses, 128 entries, GUID types, checksums and a backup copy. BIOS boots by running MBR code; UEFI boots by reading GPT to find the ESP and running a file from it.
