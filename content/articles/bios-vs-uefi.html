The problem firmware solves

An operating system lives on a disk. But right after power-on, nothing is set up to read a disk: the memory controller is not trained, RAM may not even work yet, and no driver for the storage controller exists. Something has to run first, from a chip on the motherboard, and get the machine far enough along to load the next piece of software.

That something is the firmware. Its job, in one sentence: initialize the hardware, find a bootloader, and hand over control. BIOS and UEFI are two different designs for doing that job.

What BIOS is

The BIOS (Basic Input/Output System) dates from the original IBM PC in 1981. When the CPU comes out of reset, it starts executing at a fixed address near the top of the 4 GB address space (0xFFFFFFF0 on x86), which the chipset maps to the firmware flash chip. From there the BIOS:

  1. Runs the POST (Power-On Self-Test) and initializes the CPU, memory and basic devices.
  2. Walks its boot order list: first disk, USB stick, network and so on.
  3. Reads the first 512-byte sector of the chosen disk into memory at address 0x7C00.
  4. Checks that the last two bytes are the signature 0x55 0xAA, and if so, jumps to it.

That's it. The BIOS does not understand partitions or filesystems. It trusts that whatever is in sector 0 knows what to do next. The CPU is still in 16-bit real mode, the mode of the original 8086, with access to only about 1 MB of memory. The tiny boot code calls BIOS "interrupt" services such as INT 13h to read more disk sectors.

What UEFI is

UEFI (Unified Extensible Firmware Interface) is a specification, not a single program. It defines how firmware and operating systems talk to each other before the OS is running. Intel started it as EFI in the late 1990s for Itanium; today almost every PC, most servers and many Arm systems use it.

The key difference: UEFI firmware understands filesystems and runs programs. Instead of blindly executing sector 0, it reads its list of boot entries, opens a FAT-formatted partition on the disk, finds a file such as \EFI\ubuntu\shimx64.efi, loads it as a program, and calls it. That program is the bootloader.

The EFI System Partition

UEFI needs somewhere to keep bootloaders as files. That place is the EFI System Partition (ESP): a small partition, usually 100 to 500 MB, formatted as FAT32 and marked with a special type identifier. A typical dual-boot ESP looks like this:

```text EFI/ ├── BOOT/ │ └── BOOTX64.EFI ← fallback path, used for USB sticks and fresh disks ├── Microsoft/Boot/ │ └── bootmgfw.efi ← Windows Boot Manager └── ubuntu/ ├── shimx64.efi ← signed first stage for Secure Boot └── grubx64.efi ← GRUB ```

The \EFI\BOOT\BOOTX64.EFI path (BOOTAA64.EFI on 64-bit Arm) is special: if no boot entry applies, firmware tries it on removable media. That is how an installer USB boots on any UEFI machine without configuration.

Boot entries live in NVRAM

UEFI stores boot configuration as variables in flash on the motherboard. Each Boot#### variable says "this disk, this partition, this file". BootOrder lists them in priority order. On Linux you can see them with efibootmgr:

```bash $ efibootmgr BootCurrent: 0001 BootOrder: 0001,0000,0002 Boot0000* Windows Boot Manager HD(1,GPT,...)/File(\EFI\Microsoft\Boot\bootmgfw.efi) Boot0001* ubuntu HD(1,GPT,...)/File(\EFI\ubuntu\shimx64.efi) Boot0002* UEFI: USB Drive PciRoot(0x0)/Pci(0x14,0x0)/USB(...) ```

This explains a common surprise: replacing a disk or resetting the firmware can remove the entry while the files are still on the ESP. The fix is to recreate the entry, not reinstall the OS.

Secure Boot in one paragraph

With Secure Boot enabled, UEFI checks the digital signature of every .efi file before running it. The firmware holds a database of trusted keys (db) and a list of revoked ones (dbx). A bootloader signed by a trusted key runs; anything else is refused. Linux distributions use a small program called shim, signed by Microsoft's key, which then verifies GRUB and the kernel with the distribution's own key. This chain prevents malware from inserting itself before the OS starts.

Inside UEFI: the phases

You rarely need these names, but they show up in firmware logs and debugging:

PhaseWhat happens
SEC (Security)First code after reset. Uses CPU cache as temporary RAM because DRAM is not ready.
PEI (Pre-EFI Initialization)Initializes and trains the memory controller so DRAM works.
DXE (Driver Execution Environment)Loads drivers for PCIe, USB, storage, graphics and network.
BDS (Boot Device Selection)Reads boot entries and launches the bootloader.
RT (Runtime)After the OS calls ExitBootServices(), only runtime services remain.

CSM: UEFI pretending to be BIOS

Many PCs sold during the transition included a Compatibility Support Module, which lets UEFI firmware boot old MBR disks the BIOS way. Intel ended CSM support on its client platforms around 2020, so new machines are UEFI-only. If an old disk will not boot on a new PC, this is usually why.

Common misconceptions

  • "The BIOS settings screen." People still say BIOS for the setup menu, even on UEFI machines. The setup screen and the boot interface are different things.
  • "UEFI is faster." UEFI can skip legacy work, but boot speed depends mostly on the vendor's firmware and what it initializes.
  • "UEFI requires GPT." Usually paired, but the specification can boot from an MBR disk with an ESP. Windows, however, requires GPT for UEFI installs.
Key takeaway

BIOS loads and jumps to 512 bytes from the start of a disk in 16-bit mode. UEFI initializes the platform, reads a boot entry from NVRAM, opens a FAT partition and runs a bootloader file, optionally verifying its signature. Both end the same way: a bootloader loads the OS kernel.
