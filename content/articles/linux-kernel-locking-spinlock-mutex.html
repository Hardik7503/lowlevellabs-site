Two ways to wait

When a lock is held by someone else, the waiter can either spin (loop on the CPU checking until it is free) or sleep (ask the scheduler to run something else and wake it when the lock is released).

  • A spinlock spins. While a CPU holds one, preemption is disabled on that CPU. It is cheap when held briefly and can be used where sleeping is impossible, such as interrupt handlers.
  • A mutex sleeps. It can protect long sections and sections that call functions which may sleep, but can only be used where sleeping is allowed: process context.

The rule everything follows from

Never sleep while holding a spinlock, and never take a sleeping lock in atomic context.

Atomic context includes hard interrupt handlers, softirqs and tasklets, timer callbacks, and any code holding a spinlock or running with preemption or interrupts disabled.

If a thread sleeps while holding a spinlock, the scheduler may run another thread on the same CPU that tries to take the same lock. It spins forever, because the holder cannot run to release it. On a single CPU that is an instant deadlock.

Functions that may sleep include mutex_lock(), kmalloc(GFP_KERNEL), copy_to_user() and copy_from_user() (page faults), msleep(), wait_event() and most I²C and SPI transfer functions. With CONFIG_DEBUG_ATOMIC_SLEEP enabled, calling one in atomic context prints "BUG: sleeping function called from invalid context" with a stack trace. Leave it on in development kernels.

Choosing by context

Why the _irqsave variant

Suppose process context takes a plain spin_lock(), and an interrupt arrives on the same CPU whose handler takes the same lock. The handler spins, waiting for the process-context code to release the lock, but that code cannot run until the handler returns. Deadlock.

spin_lock_irqsave() disables local interrupts before taking the lock and saves the previous interrupt state in flags; spin_unlock_irqrestore() puts it back. The _bh variants do the same for softirqs, which also cannot preempt the holder.

```c struct mydev { void __iomem *base; struct i2c_client *client; spinlock_t lock; /* protects rx_head, rx_tail, rx_buf */ unsigned int rx_head, rx_tail; u8 rx_buf[256]; struct mutex cfg_lock; /* protects configuration, may sleep */ }; /* Hard IRQ handler: interrupts are already disabled on this CPU here */ static irqreturn_t mydev_irq(int irq, void *data) { struct mydev *d = data; spin_lock(&d->lock); d->rx_buf[d->rx_head++ % 256] = readb(d->base + RXDATA); spin_unlock(&d->lock); return IRQ_HANDLED; } /* Process context reading the same ring */ static int mydev_take(struct mydev *d, u8 *out) { unsigned long flags; int ret = -EAGAIN; spin_lock_irqsave(&d->lock, flags); if (d->rx_tail != d->rx_head) { *out = d->rx_buf[d->rx_tail++ % 256]; ret = 0; } spin_unlock_irqrestore(&d->lock, flags); return ret; /* copy_to_user() happens AFTER unlocking */ } /* Configuration over I2C may sleep: mutex */ static int mydev_set_gain(struct mydev *d, u8 gain) { int ret; mutex_lock(&d->cfg_lock); ret = i2c_smbus_write_byte_data(d->client, REG_GAIN, gain); mutex_unlock(&d->cfg_lock); return ret; } ```

The comment on each lock saying what it protects is not decoration. Kernel reviewers expect it, and it is what lets the next person extend the driver without guessing.

Other tools you will meet

  • Atomics (atomic_t, refcount_t) for single counters and reference counts, without a lock.
  • RCU for read-mostly data: readers take no lock at all, writers publish a new copy and free the old one after a grace period.
  • Completions for "wait until this one event happens", such as a DMA transfer finishing. Not a lock, but often what people actually needed instead of a semaphore.
  • Read-write locks exist, but they rarely beat a plain spinlock and RCU usually serves read-heavy data better.

PREEMPT_RT changes the implementation, not the rules

On real-time kernels (CONFIG_PREEMPT_RT, merged into mainline in Linux 6.12), spinlock_t becomes a sleeping lock based on an rt_mutex with priority inheritance, and most interrupt handlers run in kernel threads. This keeps latency low. Code that follows the rules above works on both. Code that truly must spin, such as low-level interrupt-controller code, uses raw_spinlock_t, which stays a real spinlock on every configuration.

Let the tools check you

Lockdep (CONFIG_PROVE_LOCKING) records every lock ordering and context it observes and reports potential deadlocks, even ones that did not actually happen on this run, such as a lock taken with interrupts enabled in one place and from an IRQ handler in another. Run your driver's tests on a lockdep kernel before every release.

Key takeaway

List every context that touches the data. If any is a hard IRQ, use spin_lock_irqsave(); if a softirq, spin_lock_bh(); if all are process context and anything may sleep, use a mutex. Keep spinlock sections tiny and do user copies and allocations outside them.
