Why so many stages?

Each stage is limited by what exists when it runs:

  • At power-on, DRAM does not work. The memory controller must be configured and trained first, so the earliest code must fit in a small on-chip SRAM, often 64 to 256 KB.
  • The code that trains DRAM is board-specific and too big for the chip's mask ROM, so it lives in flash and is loaded by the ROM.
  • Security firmware should be separate from the bootloader and the OS so it can stay resident and protected.
  • The full bootloader, with drivers for SD cards, USB, Ethernet and filesystems, is too big for SRAM and must run from DRAM.

So each stage does one job, then loads a bigger stage into a bigger memory.

Stage by stage

1. Reset and the Boot ROM

When reset is released, the CPU fetches its first instruction from a fixed reset vector, which points into a ROM inside the SoC. Nobody can change this code; the chip vendor burned it in. It reads boot-mode pins or fuses to decide where to look (SD card, eMMC, SPI NOR, USB recovery), finds an image with a vendor-specific header, copies it into SRAM and jumps to it. On secure-boot parts it first verifies the image's signature against a key hash in fuses.

2. SPL (or BL2): making DRAM work

The Secondary Program Loader is a cut-down build of U-Boot (or, in Trusted Firmware terms, BL2). Its main job is DRAM initialization: programming the memory controller and PHY with the exact timings of the RAM chips on this board, and running training sequences. Once DRAM works, it loads the next images (BL31, U-Boot, sometimes a secure OS) into DRAM, often from a single FIT image.

3. Trusted Firmware-A BL31

On 64-bit Arm, the CPU has four exception levels: EL3 (most privileged, secure monitor), EL2 (hypervisor), EL1 (OS kernel) and EL0 (applications). BL31 runs at EL3 and stays resident after boot. Linux calls into it through PSCI (Power State Coordination Interface) to turn CPU cores on and off, suspend and reboot. BL31 then drops to EL2 and starts U-Boot.

4. U-Boot

The full bootloader has a command shell, storage and network drivers, and filesystem support. A typical boot script does this:

```bash load mmc 0:1 ${kernel_addr_r} Image # the uncompressed arm64 kernel load mmc 0:1 ${fdt_addr_r} board.dtb # the Device Tree blob load mmc 0:1 ${ramdisk_addr_r} initramfs.cpio.gz setenv bootargs console=ttyS0,115200 root=/dev/mmcblk0p2 rw earlycon booti ${kernel_addr_r} ${ramdisk_addr_r}:${filesize} ${fdt_addr_r} ```

booti checks the kernel image header, fixes up the Device Tree (adds the memory size, the command line and the initramfs location), puts the CPU in the required state and jumps.

The DTB pointer is the most important item. The kernel image is generic; the Device Tree is how it learns this board's memory size, UART address, interrupt controller and every other device. A wrong or missing DTB is the single most common reason a kernel starts and then prints nothing.

Debugging a silent board

Work forward through the chain and find the last stage that produced evidence:

SymptomLikely stageWhat to check
Nothing at all on the serial portBoot ROM or SPLBoot pins, image written at the right offset, correct image header, UART pins and baud rate
SPL prints, then hangs during DRAMSPLDRAM configuration matches the board's RAM part
U-Boot prompt works, "Starting kernel..." then silenceKernel early bootDTB matches board, earlycon on the command line, kernel built for this SoC, load addresses do not overlap
Kernel log stops at mounting rootKernel initroot= argument, storage driver built in, initramfs present
  • earlycon makes the kernel print through the UART before its normal console driver loads. It turns "silence after Starting kernel" into a real error message.
  • Overlapping load addresses are a classic bug: the kernel decompresses or the initramfs is loaded over the DTB. Check bdinfo and the sizes of each file.
  • A JTAG debugger attached at the jump can confirm x0, the exception level and the PC, which settles most handoff questions in minutes.
Key takeaway

Each boot stage exists because of a constraint: no DRAM, no drivers, separate security. Boot ROM loads SPL into SRAM; SPL trains DRAM and loads TF-A and U-Boot; U-Boot loads the kernel and DTB and jumps with the CPU in the documented state. When a board is silent, find the last stage that spoke and check its contract with the next.
