Three contexts

Process context

Code running on behalf of a task: a system call such as read() entering your driver, a kernel thread, a workqueue item. There is a current task (current) the scheduler can suspend. So this code may sleep: wait for I/O, take a mutex, allocate memory with GFP_KERNEL, copy to and from user space.

Hard IRQ context

Your handler registered with request_irq(). It runs the instant the hardware interrupt arrives, on whatever CPU took it, borrowing whatever task happened to be running. Interrupts are disabled on that CPU while it runs. It must not sleep, because there is no task of its own to put to sleep and nothing to wake it.

Softirq context

Deferred work the kernel runs soon after hard interrupts return, with interrupts enabled but still without a task to sleep. The networking stack, block-layer completions, timers and tasklets run here. It must not sleep either.

Why hard IRQ handlers must be short

  • While your handler runs, that CPU cannot service other interrupts (or only higher-priority ones). Every microsecond you spend adds latency to every other device.
  • The interrupted task, which may be a real-time thread, is frozen until you return.
  • Long handlers cause dropped packets, audio glitches and, at worst, watchdog resets.

The standard design is the top half / bottom half split.

Bottom-half options

Threaded IRQs (usually the best choice)

```c static irqreturn_t sensor_hardirq(int irq, void *data) { struct sensor *s = data; if (!(readl(s->base + IRQ_STATUS) & DATA_READY)) return IRQ_NONE; /* not ours (shared line) */ writel(DATA_READY, s->base + IRQ_CLEAR); return IRQ_WAKE_THREAD; /* run sensor_thread next */ } static irqreturn_t sensor_thread(int irq, void *data) { struct sensor *s = data; mutex_lock(&s->lock); /* allowed: we're in a kernel thread */ process_samples(s); mutex_unlock(&s->lock); return IRQ_HANDLED; } ret = devm_request_threaded_irq(dev, irq, sensor_hardirq, sensor_thread, IRQF_ONESHOT, "sensor", s); ```

Workqueues

Queue a struct work_struct with schedule_work(); a kernel worker thread runs it later in process context. Good for work triggered from anywhere, not only interrupts, and for delayed work (schedule_delayed_work()).

Tasklets and softirqs

Tasklets run in softirq context: fast, but no sleeping. They are being phased out in new code in favour of threaded IRQs and workqueues. Softirqs themselves are reserved for core subsystems.

How to tell where you are

  • in_task() is true in process context; in_interrupt() covers hard IRQ and softirq; in_hardirq() and in_softirq() are more specific.
  • Don't use these to choose behaviour at runtime ("if atomic, use GFP_ATOMIC"); design each function for a known context and document it. Use them in assertions such as might_sleep(), which warns if a function that may sleep is called from atomic context.
  • Enable CONFIG_DEBUG_ATOMIC_SLEEP in development: "BUG: sleeping function called from invalid context" points to the exact call.
Key takeaway

Process context may sleep; softirq and hard IRQ contexts may not. Keep hard IRQ handlers to acknowledging the device and scheduling work, and do everything slow, sleeping or bus-related in a threaded IRQ or workqueue.
