Why programs can't just call the kernel

A user program and the kernel run at different privilege levels. The CPU enforces the difference in hardware:

  • User code runs at EL0 on Arm64 or ring 3 on x86. It cannot touch device registers, page tables, or kernel memory.
  • The kernel runs at EL1 on Arm64 or ring 0 on x86, with full control of the machine.

If user code could simply jump into kernel code, it could jump into the middle of any function and skip every permission check. So the CPU provides exactly one controlled doorway: a special instruction that switches to kernel mode and jumps to an address the kernel chose in advance. On Arm64 that instruction is svc (supervisor call). On x86-64 it is syscall.

The whole journey in seven steps

Take one line of C, write(1, "hi\n", 3);. Whatever the architecture, it goes through the same seven steps:

Step 1: the calling convention for system calls

The kernel needs two things from the program: which service it wants (the system call number) and the arguments. Both travel in CPU registers. Each architecture defines which registers, and the convention is not the same as for ordinary function calls (compare Calling Conventions).

Two details worth noticing:

  • On x86-64 the fourth argument goes in r10, not rcx as in a normal function call. That is because the syscall instruction itself overwrites rcx (step 3 explains why).
  • System call numbers differ per architecture. write is 64 on Arm64 but 1 on x86-64. Arm64 uses the "generic" numbering shared by newer architectures such as RISC-V. Never hard-code a number; use the __NR_write constant from <asm/unistd.h> or SYS_write from <sys/syscall.h>.

What libc does

You almost never write the trap yourself. The C library wrapper puts arguments in the right registers, executes the trap, and converts the result:

```c #include #include write(1, "hi\n", 3); /* libc wrapper */ syscall(SYS_write, 1, "hi\n", 3); /* generic wrapper, any number */ ```

Steps 1–2 in assembly: a raw system call

This program calls write and exit directly with no C library. It assembles and runs on any 64-bit Arm Linux system:

```armasm // hello-arm64.S build: gcc -nostdlib -static hello-arm64.S -o hello .data msg: .ascii "hi\n" len = . - msg .text .global _start _start: mov x0, #1 // arg1: fd = 1 (stdout) ldr x1, =msg // arg2: buffer address (from literal pool) mov x2, #len // arg3: byte count mov x8, #64 // syscall number: __NR_write on arm64 svc #0 // trap into the kernel; result comes back in x0 mov x0, #0 // arg1: exit status mov x8, #93 // __NR_exit svc #0 ```

The same program on x86-64. Note the different numbers and registers:

```x86asm # hello-x86_64.S build: gcc -nostdlib -static hello-x86_64.S -o hello .intel_syntax noprefix .data msg: .ascii "hi\n" len = . - msg .text .global _start _start: mov edi, 1 # arg1: fd = 1 (writing edi zero-extends rdi) lea rsi, [rip + msg] # arg2: buffer address mov edx, len # arg3: byte count mov eax, 1 # syscall number: __NR_write on x86-64 syscall # trap; result in rax; rcx and r11 are overwritten xor edi, edi # arg1: exit status 0 mov eax, 60 # __NR_exit syscall ```

The immediate in svc #0 is ignored by Linux on Arm64. The number comes from x8; the #0 is only a convention.

Step 3 on Arm64: what the CPU does on svc

When the CPU executes svc at EL0, the hardware, not software, performs these actions in one indivisible step:

  1. Saves the address of the instruction after svc into ELR_EL1 (Exception Link Register), so the kernel knows where to return.
  2. Saves the current processor state (condition flags, interrupt masks, current EL) into SPSR_EL1 (Saved Program Status Register).
  3. Records why the exception happened in ESR_EL1 (Exception Syndrome Register). For an svc from AArch64, the exception class field is 0x15, and the low bits hold the svc immediate.
  4. Switches to EL1, masks interrupts, and selects the EL1 stack pointer SP_EL1.
  5. Jumps to the kernel's exception vector table at VBAR_EL1 + 0x400, the slot for "synchronous exception from a lower EL running AArch64".

Because the return address and state are saved in registers, the hardware has not touched memory or the stack yet. The kernel's entry code does that next.

Step 3 on x86-64: what the CPU does on syscall

The x86-64 syscall instruction was designed to be fast, so it does as little as possible. The kernel configured three model-specific registers (MSRs) at boot, and the CPU uses them:

  1. Saves the return address (the instruction after syscall) into rcx.
  2. Saves the flags register RFLAGS into r11.
  3. Clears the flag bits listed in IA32_FMASK; Linux uses it to disable interrupts and clear the direction and trap flags.
  4. Loads the kernel code and stack segment selectors from IA32_STAR, which switches the CPU to ring 0.
  5. Jumps to the address in IA32_LSTAR, which Linux sets to its entry routine entry_SYSCALL_64.

Notice what it does not do: it does not switch the stack. rsp still points at the user's stack when the kernel's first instruction runs. The kernel must fix that immediately, and it cannot trust anything on the user stack.

Step 4: kernel entry, saving the user's state

The kernel will run C code that freely uses registers. Before it does, it must save every user register so it can restore them exactly on return. Linux saves them in a structure called struct pt_regs at the top of the current thread's kernel stack. Every thread has its own kernel stack, typically 16 KB.

Arm64 entry

The vector at VBAR_EL1 + 0x400 branches to el0t_64_sync in arch/arm64/kernel/entry.S. Its kernel_entry macro stores x0–x30, the user SP_EL0, ELR_EL1 and SPSR_EL1 into pt_regs. The C handler then reads ESR_EL1 to learn the cause and, for exception class 0x15, calls the system call path. Simplified, in recent kernels:

```text el0t_64_sync (entry.S: save registers into pt_regs) └─ el0t_64_sync_handler (entry-common.c: read ESR_EL1, switch on class) └─ el0_svc └─ do_el0_svc └─ el0_svc_common (tracing, seccomp, then:) └─ invoke_syscall(regs, regs->regs[8], ...) └─ sys_call_table[nr](regs) → __arm64_sys_write ```

x86-64 entry

entry_SYSCALL_64 in arch/x86/entry/entry_64.S must do the stack switch by hand, using only the few registers it may touch:

```x86asm entry_SYSCALL_64: swapgs ; GS base now points at this CPU's per-CPU data mov QWORD PTR gs:[cpu_tss_rw+...], rsp ; stash the user rsp in per-CPU scratch mov rsp, QWORD PTR gs:[pcpu_hot+...] ; load this thread's kernel stack top push __USER_DS ; build pt_regs: ss push QWORD PTR gs:[...] ; user rsp push r11 ; rflags push __USER_CS ; cs push rcx ; rip push rax ; orig_ax (syscall nr) ; ... push the remaining general registers ... call do_syscall_64 ; C code: dispatch ```

(Abridged; the real code also handles page-table isolation and speculative-execution mitigations. Symbol names change between kernel versions.)

swapgs is the trick that makes this possible: it swaps the user's GS base with a kernel value stored in an MSR, giving the entry code a pointer to per-CPU data without using any general-purpose register.

Step 5: dispatching through the system call table

The kernel has an array of function pointers, sys_call_table, indexed by system call number. Dispatch is essentially:

```c /* Simplified from arch/arm64/kernel/syscall.c and arch/x86/entry/common.c */ if (nr < NR_syscalls) { nr = array_index_nospec(nr, NR_syscalls); /* block Spectre-style out-of-bounds speculation */ regs->ret = sys_call_table[nr](regs); /* x0 on arm64, ax on x86-64 */ } else { regs->ret = -ENOSYS; /* no such system call */ } ```

Before dispatch, the common entry path also handles seccomp (sandbox filters that can block or fail specific system calls, used by browsers and containers), ptrace (what lets strace stop the process at each call), and audit and tracepoints.

Handlers are written once with the SYSCALL_DEFINEn macro, which generates an architecture wrapper that pulls the arguments out of pt_regs:

```c /* fs/read_write.c */ SYSCALL_DEFINE3(write, unsigned int, fd, const char __user *, buf, size_t, count) { return ksys_write(fd, buf, count); } ```

Step 6: the handler does the work

The handler is ordinary kernel C running in process context on behalf of the calling thread, so it may sleep (see Kernel Contexts). For write:

  1. Look up file descriptor 1 in the process's file table to get a struct file.
  2. Check the file was opened for writing.
  3. Call the file's write operation: the terminal driver, a pipe, a filesystem, or your own driver (see From open() to read()).
  4. That code copies the data with copy_from_user(), never by dereferencing the user pointer directly.
Every argument is untrusted

A system call argument can be any value: a pointer into kernel memory, an enormous length, a negative descriptor. Handlers validate everything, and copy_from_user()/copy_to_user() refuse addresses outside user space and turn bad pointers into -EFAULT instead of a crash. Hardware helps too: Arm's PAN and x86's SMAP make the kernel fault if it touches user memory outside those helpers.

Step 7: the return path

When the handler returns, its result is stored in the saved return-value register in pt_regs. Before returning to user space, the kernel checks for pending work: a signal to deliver (which may redirect the return into a signal handler), a reschedule request (another thread should run first), and tracing hooks. Then it restores the registers from pt_regs and executes the return instruction.

Errors: how -EBADF becomes errno

The kernel returns errors as small negative numbers in the return register, for example -9 for -EBADF. The libc wrapper checks for a value between -4095 and -1, stores the positive code in the thread-local errno, and returns -1 to your program:

```c ssize_t n = write(42, "x", 1); /* fd 42 isn't open */ /* kernel returned -9 in x0/rax → libc: errno = EBADF (9), n = -1 */ if (n < 0) perror("write"); /* "write: Bad file descriptor" */ ```

Faster than a trap: the vDSO

A few system calls only read information the kernel can safely share, such as the current time. For those, the kernel maps a small shared library called the vDSO (virtual dynamic shared object) into every process. clock_gettime() and gettimeofday() run entirely in user space, reading a kernel-updated data page and the CPU's counter, with no privilege switch at all.

```bash $ cat /proc/self/maps | grep vdso 7ffd4e7f2000-7ffd4e7f4000 r-xp 00000000 00:00 0 [vdso] ```

What a system call costs

A system call that does almost nothing (such as getppid) costs on the order of a hundred nanoseconds on a modern CPU, and noticeably more when security mitigations are active. Kernel page-table isolation (KPTI), added after the Meltdown vulnerability, switches page tables on every entry and exit on affected CPUs. The overhead is why high-performance code batches work: one read of 64 KB instead of 64,000 one-byte reads, writev for several buffers, and io_uring to submit many operations with few traps.

Watch it yourself

```bash strace -e trace=write echo hi # see each system call and its return value # write(1, "hi\n", 3) = 3 strace -c ls > /dev/null # count calls and time per syscall ausyscall --dump | head # number ↔ name table for this architecture grep -w write /usr/include/asm*/unistd_64.h # where the numbers come from (path varies) sudo perf trace -s -- sleep 1 # low-overhead alternative to strace ```

Single-stepping the trap instruction in GDB also shows the hardware at work: step over svc or syscall and the registers change exactly as described, with only x0, or rax, rcx and r11, different afterwards.

Key takeaway

A system call is a controlled privilege switch. User code puts a number and arguments in registers and executes svc or syscall. The CPU saves the return point and flags (in ELR_EL1/SPSR_EL1 or rcx/r11) and jumps to an entry point the kernel set up. The kernel saves the user registers in pt_regs, dispatches through sys_call_table, runs the handler with every argument treated as untrusted, then restores the registers and returns with eret or sysretq, the result in x0 or rax.
