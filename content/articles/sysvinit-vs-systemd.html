The job of PID 1

The last thing the kernel does at boot is run /sbin/init (or whatever init= on the kernel command line names) as process 1. That process has special responsibilities:

  • Start the system: mount filesystems, bring up networking, start daemons and login prompts, in a sensible order.
  • Supervise: notice when services die and, ideally, restart them.
  • Reap orphans: any process whose parent exits is re-parented to PID 1, which must collect its exit status so it doesn't linger as a zombie.
  • Shut down: stop services in the right order, unmount filesystems and power off or reboot.
  • Never exit: if PID 1 dies, the kernel panics.

SysV init: runlevels and shell scripts

SysV init comes from AT&T's UNIX System V (1983) and was the standard Linux init until the mid-2010s. Its model is simple and fully sequential.

Runlevels

A runlevel is a numbered system state. /etc/inittab names the default one:

RunlevelTypical meaning (Red Hat style)
0Halt
1 (S)Single-user: maintenance, root only, no network
2Multi-user without network services (Debian used 2 as the full default)
3Multi-user with networking, text console
5Multi-user with a graphical login
6Reboot
```text # /etc/inittab (excerpt) format: id:runlevels:action:process # boot to runlevel 3 id:3:initdefault: # run once at boot: mount filesystems, fsck, set hostname si::sysinit:/etc/rc.d/rc.sysinit # entering runlevel 3: run its scripts and wait for them l3:3:wait:/etc/rc.d/rc 3 # login prompt on tty1; restart it whenever it exits 1:2345:respawn:/sbin/mingetty tty1 ```

The rc directories

Each service has one shell script in /etc/init.d/ that accepts start, stop, restart and status. Each runlevel has a directory, /etc/rcN.d/, containing symlinks to those scripts. The name of the link encodes everything:

Tools such as update-rc.d (Debian) and chkconfig (Red Hat) create these links from comment headers in the script.

Strengths and weaknesses

  • Simple and transparent. It's shell scripts. You can read every line that runs at boot, and debug with sh -x.
  • Slow. Everything runs one at a time. A script waiting 10 seconds for DHCP holds up every service after it, even ones that don't need the network.
  • Ordering by number, not by need. The numbers say "after", but nothing says "requires". If a dependency fails, later scripts start anyway.
  • Weak supervision. Once a daemon forks into the background, init forgets it. If it crashes, nothing restarts it (except entries marked respawn in inittab).
  • Fragile process tracking. stop relies on PID files. A daemon that forks helpers, or a stale PID file, leaves stray processes or kills the wrong one.
  • Every script reinvents the wheel: daemonizing, PID files, logging, privilege dropping.

systemd: units, dependencies and cgroups

systemd (2010) is a different model. Instead of scripts, it reads unit files: short declarative descriptions of what to run and what it depends on. From those it builds a dependency graph and starts everything it can in parallel.

Unit types

UnitDescribes
.serviceA daemon or one-shot task
.targetA synchronization point grouping other units: the replacement for runlevels
.socketA listening socket; starts its service on the first connection (socket activation)
.timerA schedule that starts a service, replacing many cron jobs
.mount, .automountFilesystems (generated from /etc/fstab)
.device, .path, .sliceHardware appearing via udev, file changes, cgroup resource groups

Booting as a graph

systemd's goal is a target, normally default.target → multi-user.target or graphical.target. It works out every unit that target needs, orders them by their After=/Before= relationships, and starts each one as soon as its own dependencies are ready.

Two kinds of relationship, often confused:

  • Requirement (Wants=, Requires=): "if you start me, also start that". Requires= additionally stops this unit if that one fails.
  • Ordering (After=, Before=): "if both are being started, start that one first". On its own it doesn't pull anything in.

You usually need both: Wants=network-online.target plus After=network-online.target.

Every service in its own cgroup

This is systemd's most important technical change. Each service is placed in its own cgroup (for example /system.slice/myapp.service). Every process the service forks stays in that cgroup, whatever it does to escape its parent. So systemd always knows exactly which processes belong to a service: systemctl stop can kill all of them, systemctl status can list them, and resource limits apply to the whole service. No PID files needed.

The same service, written both ways

Suppose we have a daemon, /usr/local/bin/myapp, that should run as user myapp, start after the network and restart if it crashes.

SysV init script

```bash #!/bin/sh ### BEGIN INIT INFO # Provides: myapp # Required-Start: $network $syslog # Required-Stop: $network $syslog # Default-Start: 2 3 4 5 # Default-Stop: 0 1 6 # Short-Description: My application daemon ### END INIT INFO DAEMON=/usr/local/bin/myapp PIDFILE=/var/run/myapp.pid USER=myapp case "$1" in start) echo "Starting myapp" start-stop-daemon --start --quiet --background --make-pidfile \ --pidfile "$PIDFILE" --chuid "$USER" --exec "$DAEMON" -- --config /etc/myapp.conf ;; stop) echo "Stopping myapp" start-stop-daemon --stop --quiet --retry=TERM/10/KILL/5 --pidfile "$PIDFILE" rm -f "$PIDFILE" ;; restart) "$0" stop "$0" start ;; status) if [ -f "$PIDFILE" ] && kill -0 "$(cat "$PIDFILE")" 2>/dev/null; then echo "myapp is running"; exit 0 else echo "myapp is stopped"; exit 3 fi ;; *) echo "Usage: $0 {start|stop|restart|status}"; exit 1 ;; esac exit 0 ``` ```bash cp myapp /etc/init.d/myapp && chmod +x /etc/init.d/myapp update-rc.d myapp defaults # create S/K links (chkconfig --add myapp on Red Hat) service myapp start ```

Notice what's missing: if myapp crashes at 3 a.m., it stays down. Its output goes nowhere unless the program handles logging itself.

systemd unit file

```ini # /etc/systemd/system/myapp.service [Unit] Description=My application daemon Wants=network-online.target After=network-online.target [Service] Type=exec User=myapp ExecStart=/usr/local/bin/myapp --config /etc/myapp.conf Restart=on-failure RestartSec=2 # Resource limits (cgroup) and hardening, for free MemoryMax=256M CPUQuota=50% NoNewPrivileges=yes ProtectSystem=strict PrivateTmp=yes [Install] WantedBy=multi-user.target ``` ```bash systemctl daemon-reload # re-read unit files systemctl enable --now myapp # start at boot (link into multi-user.target.wants) and now systemctl status myapp # state, PID, cgroup tree, last log lines journalctl -u myapp -f # its stdout/stderr, collected by journald ```

Fifteen lines of configuration replace a 40-line script, and add things the script never had: automatic restart, captured logs, a memory and CPU cap, and sandboxing. The program itself just runs in the foreground and writes to stdout; it doesn't need to daemonize or manage a PID file.

Choosing Type=

exec or simple: the program stays in the foreground (best). forking: legacy daemons that fork into the background; pair with PIDFile=. notify: the program calls sd_notify("READY=1") when it's truly ready, so dependent units wait for real readiness. oneshot: a task that runs and exits, such as loading firmware or applying settings.

For compatibility, systemd still runs old /etc/init.d scripts (it generates units for them), accepts service and telinit commands, and provides runlevel3.target as an alias of multi-user.target.

What about embedded Linux?

  • BusyBox init with a simple /etc/inittab and /etc/init.d/rcS is still common on small devices: a few hundred kilobytes, a sub-second boot, and nothing to configure.
  • SysV-style init (sysvinit) remains Yocto's default in some setups and is easy to audit.
  • systemd is the usual choice on larger devices (gateways, infotainment, industrial PCs) where supervision, watchdog integration (WatchdogSec= with the hardware watchdog), journald and resource limits are worth its size. Both Yocto and Buildroot can build either.
Key takeaway

PID 1 starts, supervises and stops everything in user space. SysV init does it with shell scripts run one by one in numbered order for each runlevel, tracking daemons with PID files. systemd does it with declarative unit files, a dependency graph that starts units in parallel, cgroups to track every process of a service, built-in restart, logging and resource limits, and targets in place of runlevels.
