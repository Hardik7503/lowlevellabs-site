The scheduling rule

Most real-time operating systems, including VxWorks, FreeRTOS, Zephyr and ThreadX, use fixed-priority preemptive scheduling. Every task has a priority. Whenever a higher-priority task becomes ready (an interrupt gives it a semaphore, a timer expires), the scheduler preempts whatever is running and switches to it immediately.

That rule is what makes response times analysable: a high-priority task only waits for tasks of equal or higher priority, plus interrupt handlers. Priority inversion is any situation where a high-priority task ends up waiting for a lower-priority one.

Bounded inversion is normal

Suppose a low-priority task L holds a mutex protecting a shared buffer, and high-priority task H wants it. H blocks until L releases it. That is inversion, but it is bounded: H waits at most as long as L's critical section, which you can measure and keep short. Every system with shared resources has some of this.

Unbounded inversion is the bug

Now add a medium-priority task M that does not use the mutex at all.

  1. L takes the mutex.
  2. H becomes ready, preempts L, tries to take the mutex and blocks.
  3. M becomes ready. It outranks L, so it preempts L.
  4. L cannot run, so it cannot release the mutex, so H cannot run. H now waits for M to finish, and for any other medium-priority task that shows up.

H's worst-case latency is no longer bounded by a short critical section. It depends on the CPU load of unrelated tasks.

Mars Pathfinder, 1997

Pathfinder ran VxWorks. A high-priority bus-management task and a low-priority meteorological data task shared an information bus protected by a mutex. Medium-priority communications tasks occasionally ran long enough while the low-priority task held the mutex that the bus task missed its deadline. A watchdog noticed and reset the whole system, repeatedly.

JPL engineers reproduced it on a ground replica using the system's trace logging. The mutex had been created without priority inheritance enabled. They uploaded a small patch that switched it on, and the resets stopped. The lesson engineers still repeat: the fix existed in the RTOS all along, it just was not turned on.

Fix 1: priority inheritance

With priority inheritance, when H blocks on a mutex held by L, the kernel temporarily raises L's priority to H's. M can no longer preempt L. L finishes its critical section quickly, releases the mutex, drops back to its own priority, and H runs.

Inheritance is transitive in good implementations: if L is itself blocked on another mutex held by an even lower task, the boost propagates down the chain.

Fix 2: priority ceiling

With the priority ceiling protocol (immediate ceiling in its common form), each mutex is assigned a ceiling equal to the highest priority of any task that will ever lock it. Any task that takes the mutex immediately runs at the ceiling until it releases it.

Turning it on in practice

VxWorks

```c SEM_ID busLock = semMCreate(SEM_Q_PRIORITY | SEM_INVERSION_SAFE | SEM_DELETE_SAFE); semTake(busLock, WAIT_FOREVER); /* short critical section */ semGive(busLock); ```

SEM_INVERSION_SAFE enables inheritance and requires SEM_Q_PRIORITY, so that the highest-priority waiter is the one that gets the mutex next.

FreeRTOS

```c SemaphoreHandle_t lock = xSemaphoreCreateMutex(); /* mutexes inherit priority */ if (xSemaphoreTake(lock, pdMS_TO_TICKS(10)) == pdTRUE) { /* critical section */ xSemaphoreGive(lock); } ```

FreeRTOS mutexes implement inheritance; binary semaphores do not. Using xSemaphoreCreateBinary() as a lock is a classic way to reintroduce the Pathfinder bug.

POSIX threads

```c pthread_mutexattr_t a; pthread_mutexattr_init(&a); pthread_mutexattr_setprotocol(&a, PTHREAD_PRIO_INHERIT); pthread_mutex_init(&lock, &a); ```

Design rules that matter more than the protocol

  • Keep critical sections short and bounded. No blocking calls, no logging to slow devices, no waiting on other locks inside them.
  • Use a mutex, not a semaphore, for mutual exclusion. Only mutexes have an owner, and only an owner can be boosted.
  • Prefer message passing for cross-priority data. If H only needs the latest sample, a queue or double buffer avoids sharing a lock at all.
  • Trace it. Pathfinder was diagnosed from a trace. Tools such as VxWorks System Viewer, Tracealyzer or SEGGER SystemView show inversion as a gap where the high-priority task is blocked while a medium task runs.
Key takeaway

Priority inversion is unavoidable when tasks share resources. Unbounded inversion is a design bug. Lock shared resources with an inheritance-capable mutex (or use ceilings), keep critical sections short, and verify with a trace.
