The whole journey at a glance

Step 1: device numbers connect the file to the driver

A device file like /dev/ttyS0 contains no data. It is an inode that records two numbers:

```bash $ ls -l /dev/ttyS0 /dev/null crw-rw---- 1 root dialout 4, 64 Nov 20 09:00 /dev/ttyS0 crw-rw-rw- 1 root root 1, 3 Nov 20 09:00 /dev/null ```

The c means character device. 4, 64 is the major and minor number. The major number selects the driver (4 is the serial TTY driver); the minor number tells that driver which of its devices is meant (64 is the first serial port).

A driver claims numbers and connects them to its operations when it registers:

```c static dev_t devno; static struct cdev my_cdev; alloc_chrdev_region(&devno, 0, 1, "mydrv"); /* get a free major, 1 minor */ cdev_init(&my_cdev, &mydrv_fops); /* tie numbers to operations */ cdev_add(&my_cdev, devno, 1); /* now live */ cls = class_create("mydrv"); /* (older kernels: THIS_MODULE first) */ device_create(cls, NULL, devno, NULL, "mydrv0");/* udev creates /dev/mydrv0 */ ```

The misc device framework wraps all of this in one call when you need a single device node.

Step 2: open() builds a struct file

When a program calls open("/dev/mydrv0", O_RDONLY), the VFS resolves the path, sees a character device inode, looks up the cdev registered for that major/minor, and creates a struct file: the kernel's record of this particular open. It holds the file position (f_pos), the open flags, a pointer to the driver's file_operations, and a private_data pointer for the driver's use.

The kernel stores a pointer to that struct file in the process's file descriptor table and returns the slot index, say 3. That small integer is all user space ever sees.

If the driver supplies .open, it is called now. That is the place to find the device from the minor number, store it in file->private_data, and power it up if needed:

```c static int mydrv_open(struct inode *inode, struct file *file) { struct mydev *d = container_of(inode->i_cdev, struct mydev, cdev); file->private_data = d; /* later calls get the device from here */ return 0; } ```

Step 3: read() reaches the driver

read(3, buf, 64) traps into the kernel. The kernel fetches struct file from slot 3, checks the file was opened for reading, and calls file->f_op->read(file, buf, 64, &file->f_pos).

```c static ssize_t mydrv_read(struct file *file, char __user *buf, size_t count, loff_t *ppos) { struct mydev *d = file->private_data; u8 kbuf[64]; size_t n; /* Block until data arrives, unless the user asked not to */ if (fifo_empty(d)) { if (file->f_flags & O_NONBLOCK) return -EAGAIN; if (wait_event_interruptible(d->wq, !fifo_empty(d))) return -ERESTARTSYS; /* interrupted by a signal */ } n = fifo_pop(d, kbuf, min(count, sizeof(kbuf))); if (copy_to_user(buf, kbuf, n)) return -EFAULT; return n; /* bytes delivered; 0 would mean EOF */ } ```

Step 4: the return value goes back up

The driver's return value travels back unchanged: a positive count becomes read()'s return value, and a negative error such as -EAGAIN becomes -1 with errno = EAGAIN in user space.

The read() contract

ReturnMeaning to the caller
n > 0n bytes were copied. May be less than requested; that's normal.
0End of file. cat stops. Never return 0 just because no data is ready yet.
-EAGAINNo data now, and the file is non-blocking.
-ERESTARTSYSA signal interrupted the wait; the kernel restarts or fails the call.
-EFAULTThe user buffer was invalid.

Other operations you'll add

  • .write: the mirror image, using copy_from_user().
  • .poll: lets poll(), select() and epoll wait on your device alongside sockets and pipes.
  • .unlocked_ioctl: device-specific commands that don't fit read/write. See Designing a Robust ioctl Interface.
  • .mmap: map device memory or a DMA buffer directly into the process, for zero-copy access.
  • .release: called when the last reference to the struct file is closed, not on every close() if the descriptor was duplicated.

Watch it happen

```bash strace -e trace=openat,read,close cat /dev/mydrv0 # openat(AT_FDCWD, "/dev/mydrv0", O_RDONLY) = 3 # read(3, "hello\n", 131072) = 6 # read(3, ...) <- blocks here until more data ```
Key takeaway

The major/minor number in the device file leads the VFS to your cdev; open() creates a struct file whose f_op points to your operations; every later call on that descriptor dispatches through it. Your driver only implements the last step: move data with copy_to_user()/copy_from_user() and return the right count or error.
