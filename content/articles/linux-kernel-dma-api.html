DMA in one picture

Direct Memory Access means a device reads or writes system memory itself, instead of the CPU copying every byte. The CPU's job shrinks to three things: prepare a buffer, tell the device where it is, and react when the transfer finishes. (For the basics of polling, interrupts and DMA, see Interrupts vs Polling vs DMA.)

There are two hardware arrangements, and Linux handles both with the same core API:

The three addresses

The single most important idea in Linux DMA is that one buffer has three different addresses, and the device must be given the right one:

On a simple board, the DMA address may equal the physical address. But with an IOMMU (an MMU for devices: Arm SMMU, Intel VT-d, AMD-Vi) the device sees its own virtual addresses (IOVAs). On other systems the bus adds an offset, or the device can only reach the first 4 GB. A driver that writes virt_to_phys(buf) into a device register works on one board and corrupts memory on the next. Always use the dma_addr_t the API gives you.

Step 0: tell the kernel what the device can reach

Many devices can only generate 32-bit addresses, or 36, or 40. Declare this once in probe():

```c ret = dma_set_mask_and_coherent(dev, DMA_BIT_MASK(32)); /* device emits 32-bit addresses */ if (ret) return dev_err_probe(dev, ret, "no suitable DMA available\n"); ```

If a buffer later sits above what the device can reach and there is no IOMMU, the kernel transparently copies it through a bounce buffer (swiotlb) below the limit. That works, but costs a memory copy per transfer, so set the mask as wide as the hardware really supports.

Streaming mappings and buffer ownership

A streaming mapping hands a buffer back and forth between the CPU and the device. At any moment exactly one of them owns it, and only the owner may touch it. The map, unmap and sync calls are the hand-offs, and they do whatever cache maintenance or bouncing the platform needs (see DMA and Cache Coherency).

Example 1: a bus-mastering device with a descriptor ring

This is the pattern used by network cards, NVMe drives and most PCIe devices. The device reads a ring of descriptors from memory. Each descriptor points to a data buffer. The ring is long-lived and shared continuously, so it's a coherent allocation; the data buffers change every transfer, so they're streaming mappings.

```c struct my_desc { /* layout defined by the device's datasheet */ __le64 addr; __le16 len; __le16 flags; /* DESC_OWN_HW, DESC_DONE, ... */ __le32 reserved; }; struct my_ring { struct my_desc *desc; /* CPU address of the ring */ dma_addr_t desc_dma; /* device address of the ring */ struct sk_buff *skb[RING_SIZE]; dma_addr_t buf_dma[RING_SIZE]; unsigned int tail; }; /* probe(): allocate the ring once */ ring->desc = dma_alloc_coherent(dev, RING_SIZE * sizeof(*ring->desc), &ring->desc_dma, GFP_KERNEL); if (!ring->desc) return -ENOMEM; writel(lower_32_bits(ring->desc_dma), priv->base + REG_TX_RING_LO); writel(upper_32_bits(ring->desc_dma), priv->base + REG_TX_RING_HI); /* transmit one packet */ static int my_xmit(struct my_priv *priv, struct sk_buff *skb) { struct my_ring *ring = &priv->tx; unsigned int i = ring->tail % RING_SIZE; dma_addr_t dma; dma = dma_map_single(priv->dev, skb->data, skb->len, DMA_TO_DEVICE); /* 1 */ if (dma_mapping_error(priv->dev, dma)) return -ENOMEM; ring->skb[i] = skb; ring->buf_dma[i] = dma; ring->desc[i].addr = cpu_to_le64(dma); /* 2 */ ring->desc[i].len = cpu_to_le16(skb->len); dma_wmb(); /* descriptor contents before ownership bit */ ring->desc[i].flags = cpu_to_le16(DESC_OWN_HW); ring->tail++; writel(ring->tail % RING_SIZE, priv->base + REG_TX_TAIL); /* 4: doorbell */ return 0; } /* completion interrupt (or NAPI poll): give buffers back to the CPU */ static void my_tx_clean(struct my_priv *priv, unsigned int i) { struct my_ring *ring = &priv->tx; dma_unmap_single(priv->dev, ring->buf_dma[i], ring->skb[i]->len, DMA_TO_DEVICE); /* 5 */ dev_consume_skb_any(ring->skb[i]); ring->skb[i] = NULL; } ```

Points that matter in this code:

  • cpu_to_le64(): the descriptor format is fixed by hardware, usually little-endian, so the driver converts. It costs nothing on little-endian CPUs and makes the driver correct everywhere.
  • dma_wmb(): a barrier so the device can never see the "owned by hardware" flag before the address and length are written. Without it, a weakly ordered CPU may reorder the stores and the device sends garbage.
  • writel() to the tail register includes the ordering needed so all earlier memory writes are visible to the device before the doorbell.
  • dma_mapping_error() must be checked: mapping can fail when an IOMMU or bounce pool runs out of space.

Receive is the mirror image

For receive, the driver pre-maps empty buffers with DMA_FROM_DEVICE and puts them in the ring. When the device has filled one, the driver calls dma_sync_single_for_cpu() (or unmaps) before reading the data. If it recycles the buffer, it calls dma_sync_single_for_device() before handing it back.

Example 2: a peripheral using a DMA controller (dmaengine)

A UART, SPI or audio controller on an SoC usually has no DMA engine of its own. It has a request line to a shared system DMA controller. Linux exposes those controllers through the dmaengine framework, so a SPI driver doesn't need to know whether the SoC uses a PL330, an EDMA or an SDMA.

The Device Tree connects the peripheral to its channels:

```dts spi0: spi@ff110000 { compatible = "vendor,my-spi"; reg = <0xff110000 0x1000>; dmas = <&dmac 12>, <&dmac 13>; /* controller + request line numbers */ dma-names = "tx", "rx"; }; ``` ```c #include #include #include struct my_spi { struct device *dev; void __iomem *base; phys_addr_t phys; /* physical address of the register block */ struct dma_chan *rx_chan; struct completion rx_done; }; /* probe(): get and configure the channel once */ static int my_spi_dma_init(struct my_spi *ms) { struct dma_slave_config cfg = { .direction = DMA_DEV_TO_MEM, .src_addr = ms->phys + REG_RX_FIFO, /* device FIFO: fixed address */ .src_addr_width = DMA_SLAVE_BUSWIDTH_1_BYTE, .src_maxburst = 8, /* match the FIFO threshold */ }; return dmaengine_slave_config(ms->rx_chan, &cfg); } static void my_spi_rx_callback(void *param) { struct my_spi *ms = param; complete(&ms->rx_done); /* runs in tasklet/IRQ context */ } /* receive len bytes into buf (a kmalloc'ed buffer, never on the stack) */ static int my_spi_dma_rx(struct my_spi *ms, void *buf, size_t len) { struct device *dmadev = ms->rx_chan->device->dev; /* map for the DMA controller */ struct dma_async_tx_descriptor *desc; dma_addr_t dma; int ret = 0; dma = dma_map_single(dmadev, buf, len, DMA_FROM_DEVICE); if (dma_mapping_error(dmadev, dma)) return -ENOMEM; desc = dmaengine_prep_slave_single(ms->rx_chan, dma, len, DMA_DEV_TO_MEM, DMA_PREP_INTERRUPT); if (!desc) { ret = -EIO; goto unmap; } desc->callback = my_spi_rx_callback; desc->callback_param = ms; reinit_completion(&ms->rx_done); dmaengine_submit(desc); /* queue it */ dma_async_issue_pending(ms->rx_chan); /* actually start */ writel(CTRL_RX_DMA_EN, ms->base + REG_CTRL); /* let the SPI raise DMA requests */ if (!wait_for_completion_timeout(&ms->rx_done, msecs_to_jiffies(100))) { dmaengine_terminate_sync(ms->rx_chan); /* stop a stuck transfer */ ret = -ETIMEDOUT; } unmap: dma_unmap_single(dmadev, dma, len, DMA_FROM_DEVICE); /* buffer back to CPU */ return ret; } ```

Three details people get wrong:

  • Map with the DMA controller's device, not the peripheral's: the controller is what performs the memory access, so its IOMMU and address limits apply.
  • The FIFO address is a physical register address (src_addr), taken from the resource, not the ioremap()ed pointer.
  • Never DMA into the stack or into memory from vmalloc(). Stack buffers may share cache lines with live variables, and with CONFIG_VMAP_STACK they aren't physically contiguous. Use kmalloc() or the DMA API's own allocations.

Scatter-gather: many pieces, one transfer

Large buffers in Linux are rarely physically contiguous: a 1 MB user buffer is 256 separate 4 KB pages. A scatterlist describes all the pieces, and dma_map_sg() maps them in one call. With an IOMMU, it may even merge them into one contiguous range from the device's point of view.

```c int n = dma_map_sg(dev, sgt->sgl, sgt->orig_nents, DMA_FROM_DEVICE); if (!n) return -ENOMEM; for_each_sg(sgt->sgl, sg, n, i) /* use the returned count, not orig_nents */ program_desc(i, sg_dma_address(sg), sg_dma_len(sg)); /* ... transfer ... */ dma_unmap_sg(dev, sgt->sgl, sgt->orig_nents, DMA_FROM_DEVICE); /* original count here */ ```

Debugging DMA

  • CONFIG_DMA_API_DEBUG checks every call at runtime: unmapping with the wrong size or direction, forgetting to check for mapping errors, touching a buffer while the device owns it, leaking mappings at driver unload. Turn it on in development kernels.
  • IOMMU faults in dmesg (for example "arm-smmu: Unhandled context fault: iova=0x…") mean the device used an address that was never mapped for it: usually a stale, unmapped or hand-computed address.
  • /sys/kernel/debug/dmaengine/summary lists DMA controllers, their channels and which drivers hold them.
  • Data correct on x86, corrupted on Arm almost always means missing sync calls or barriers: x86 PCIe DMA is cache-coherent and forgiving; many Arm SoCs aren't.
Key takeaway

Set the device's DMA mask in probe. Use dma_alloc_coherent() for long-lived shared structures such as descriptor rings, and streaming dma_map_*() calls for data buffers, treating map and unmap as handing ownership to and from the device. Program the device only with the returned dma_addr_t. Peripherals without their own DMA engine use dmaengine: request a channel, configure it, prepare, submit, issue pending, and wait for the callback.
