One address space, two regions

Each process gets its own virtual address space: a range of addresses it can use, from 0 up to the architecture's limit. On a 32-bit CPU, addresses are 32 bits wide, so the range is 232 bytes, 4 GB.

Linux divides that 4 GB into two parts:

  • User space: the lower part, where the program's code, data, heap, stack and libraries live. The program can access it directly.
  • Kernel space: the upper part, where the kernel's code and data are mapped. The program can't touch it; any attempt causes a fault (a segmentation fault).

On 32-bit x86 and 32-bit Arm, the default split is 3 GB user, 1 GB kernel. That's the 3:1 ratio, often described as "1:3 kernel to user". The boundary sits at address 0xC0000000, which the kernel calls PAGE_OFFSET.

Why is the kernel inside every process?

It might seem cleaner to give the kernel its own separate address space. Linux maps it into every process instead, for practical reasons:

  1. System calls and interrupts are fast. When a program makes a system call or an interrupt arrives (see How System Calls Work), the CPU only changes privilege level. The kernel's code and data are already mapped, so no page-table switch is needed, and the TLB entries stay valid.
  2. The kernel can reach user memory directly. During read(), the kernel copies data straight into the caller's buffer with copy_to_user(), because the user's pages are mapped in the same address space at that moment.
  3. One copy serves everyone. The kernel's mappings are identical in all processes, so the page tables for the kernel region are shared instead of being duplicated per process.

Protection comes from the page-table entries, not from separation. Kernel pages are marked "supervisor only": the U/S bit on x86, the AP bits on Arm. A user-mode access to them faults, even though they're mapped.

Meltdown changed this a little

In 2018 the Meltdown vulnerability showed that some CPUs could leak kernel memory through speculative execution, even with the protection bits set. The fix, KPTI (kernel page-table isolation), gives each process a second set of page tables with almost no kernel mappings while user code runs, and switches on every kernel entry and exit. The address layout stays the same; only what is actually mapped at user time shrinks. CPUs that aren't affected skip KPTI.

Why exactly 3:1?

The split is a trade-off between two needs that both want more of the same 4 GB:

  • Programs want a big user space. Databases, browsers and anything that maps large files run out of address space before they run out of RAM. 3 GB was a good amount for 1990s and 2000s software.
  • The kernel wants to map physical RAM. Linux keeps a direct map (or "linear map") where physical address P appears at virtual address PAGE_OFFSET + P. That makes it fast and simple for the kernel to reach any page. But with only 1 GB of kernel space, and room needed for other things (vmalloc, I/O mappings), only about 896 MB of RAM fits in the direct map on 32-bit x86.

RAM above that line is highmem. The kernel can still use it, mostly for user pages and page cache, but must map it temporarily (kmap_local_page()) each time it needs to touch it, which is slower and more complex.

The split is a build-time choice. Kernel configs offer VMSPLIT_3G (the default), VMSPLIT_2G (2 GB user, 2 GB kernel, more lowmem, used on many 32-bit Arm boards with 1 to 2 GB of RAM) and VMSPLIT_1G. On Arm the boundary is likewise PAGE_OFFSET.

On 64-bit, the problem disappears

64-bit CPUs don't use all 64 address bits. Typical systems use 48: that's 256 TB of virtual address space, split down the middle.

The halves sit at opposite ends of the 64-bit range with a huge unusable "hole" between them. Addresses in the hole are non-canonical and fault immediately. With tens of terabytes available, the kernel maps all physical RAM directly, highmem isn't needed, and the 3:1 trade-off is history. You'll still meet it on 32-bit embedded Linux.

Arm64 makes the split explicit in hardware: it has two translation base registers. Addresses with the top bits all zero are translated through TTBR0_EL1 (the user tables, switched per process), and addresses with the top bits all one go through TTBR1_EL1 (the kernel tables, shared).

How processes are kept apart

Every process has its own page tables, the data structure the MMU uses to translate virtual addresses to physical addresses (see Virtual Memory: MMU Page Walks and the TLB). The kernel builds and owns those tables; user code can't modify them.

That gives isolation for free:

  • The same virtual address, say 0x00400000, appears in both process A and process B, but their page tables point it at different physical pages.
  • A process can only reach physical memory its page tables map. There is no address it can write that leads into another process's pages, because no entry in its own tables points there.
  • On a context switch, the kernel loads the next process's table base into CR3 (x86) or TTBR0_EL1 (Arm64), and the whole user half of the address space changes at once.

So when people say "two processes can't access each other's memory", the precise statement is: neither process has a page-table entry pointing to the other's physical pages, and only the kernel can create one.

Sharing on purpose: the kernel maps the same page twice

Sometimes processes should share memory: a camera service handing frames to a video encoder, a database with several worker processes, a producer and consumer exchanging large buffers. Copying through a pipe or socket costs time and memory bandwidth.

The solution follows directly from the isolation mechanism: if isolation means "no page-table entry points at your pages", then sharing means the kernel adds entries in both processes' tables that point to the same physical pages. Only the kernel can do this, and only when both processes ask for it through a system call that passes permission checks.

Example: POSIX shared memory

These two programs share 4 KB through a named object. The writer creates and fills it; the reader, a completely separate process, maps the same object and reads it. Run the writer, then the reader.

```c /* shm_writer.c build: gcc shm_writer.c -o shm_writer */ #include #include #include #include #include #define SHM_NAME "/lll_demo" #define SHM_SIZE 4096 int main(void) { int fd = shm_open(SHM_NAME, O_CREAT | O_RDWR, 0600); /* 1. create a named object */ if (fd < 0) { perror("shm_open"); return 1; } if (ftruncate(fd, SHM_SIZE) < 0) { perror("ftruncate"); return 1; } /* 2. set its size */ char *p = mmap(NULL, SHM_SIZE, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0); /* 3. map it into this process */ if (p == MAP_FAILED) { perror("mmap"); return 1; } close(fd); /* the mapping stays valid */ snprintf(p, SHM_SIZE, "hello from pid %d", getpid()); /* 4. plain memory write */ printf("writer: mapped at %p, wrote \"%s\"\n", (void *)p, p); return 0; } ``` ```c /* shm_reader.c build: gcc shm_reader.c -o shm_reader */ #include #include #include #include #define SHM_NAME "/lll_demo" #define SHM_SIZE 4096 int main(void) { int fd = shm_open(SHM_NAME, O_RDONLY, 0); if (fd < 0) { perror("shm_open"); return 1; } const char *p = mmap(NULL, SHM_SIZE, PROT_READ, MAP_SHARED, fd, 0); if (p == MAP_FAILED) { perror("mmap"); return 1; } close(fd); printf("reader: mapped at %p, read \"%s\"\n", (const void *)p, p); shm_unlink(SHM_NAME); /* remove the name when done */ return 0; } ``` ```bash $ ./shm_writer && ./shm_reader writer: mapped at 0x7f106eadb000, wrote "hello from pid 171" reader: mapped at 0x7f00f1ebe000, read "hello from pid 171" ```

Look at the two addresses: they're different. Each process sees the shared page wherever the kernel placed it in its address space, yet both reach the same physical page. The data even outlived the writer process, because the kernel keeps the object until shm_unlink() and the last unmap. (On older glibc, link with -lrt.)

What the kernel does at each step

CallKernel's job
shm_open()Creates or opens a file in /dev/shm, a RAM-backed tmpfs filesystem. Checks permissions like any file.
ftruncate()Sets the object's size. No RAM is allocated yet.
mmap(MAP_SHARED)Reserves a range of virtual addresses in the caller and records a mapping (a VMA) that refers to the object. Still no page-table entries.
First accessPage fault. The kernel finds or allocates the physical page in the object's page cache, adds a page-table entry, and the access retries. The second process faulting on the same offset finds the same page.
munmap() / exitRemoves the page-table entries and drops a reference. Pages are freed only when nothing references them.

This is the "shared memory pool" role of the kernel: it owns the physical pages, decides who may map them, counts references, and frees them when the last user goes away.

Sharing memory doesn't synchronize it

Once two processes share a page, they have exactly the same problems as two threads sharing a variable: races, partial updates and memory-ordering issues. Protect shared structures with a process-shared mutex (pthread_mutexattr_setpshared()), a semaphore placed in the shared region (sem_init(&s, 1, 0)), or lock-free techniques with C11 atomics. And never store ordinary pointers inside shared memory: each process maps it at a different address, so store offsets instead.

Key takeaway

32-bit Linux splits each 4 GB address space 3 GB user and 1 GB kernel, so the kernel is mapped (but protected) in every process for fast system calls, at the cost of limiting how much RAM it can map directly. 64-bit splits a vast space evenly and removes that limit. Processes are isolated because each has its own page tables; they share memory only when the kernel deliberately maps the same physical pages into both, then tracks and frees those pages for them.
