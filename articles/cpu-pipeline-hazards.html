Inside a CPU Pipeline: Hazards, Forwarding and Branch Prediction

A pipelined CPU works on several instructions at once, like an assembly line. Almost everything interesting about CPU performance comes from the moments when that line has to stop.

10 min read20 Nov 2026

On this page

  1. Why pipeline at all
  2. The classic five stages
  3. Hazards: when the line must stop
  4. Why firmware engineers should care

Why pipeline at all

Executing one instruction involves several steps: fetch it, decode it, compute, access memory, write the result. A non-pipelined CPU does all of them for one instruction before starting the next, so most of its hardware sits idle most of the time.

A pipeline splits the work into stages separated by registers. Each clock cycle every stage works on a different instruction. Latency per instruction does not improve, but throughput approaches one instruction per cycle.

The classic five stages

StageNameWork done
IFInstruction fetchRead the instruction at PC from the instruction cache; predict the next PC.
IDDecodeDecode the opcode and read source registers from the register file.
EXExecuteALU operation, address calculation or branch comparison.
MEMMemoryLoad or store through the data cache.
WBWrite backWrite the result into the register file.

This is the textbook MIPS-style pipeline. Real cores such as a Cortex-A78 or a modern x86 have many more stages and execute out of order, but they face the same hazards and use the same ideas to hide them.

Hazards: when the line must stop

A hazard is anything that prevents the next instruction from entering the next stage on the next cycle. There are three kinds.

Data hazards

The common case is read-after-write (RAW): an instruction needs a result that an earlier instruction has not written back yet.

add  x1, x2, x3     // x1 produced at the end of EX (cycle 3)
sub  x4, x1, x5     // needs x1 at the start of its EX (cycle 4)

Without help, sub would read the old x1 in ID, or wait until add reaches WB, costing several cycles. Forwarding (bypassing) fixes this: extra paths carry the ALU result from the EX/MEM pipeline register straight back to the ALU input, so sub uses the new value with no delay.

The load-use hazard cannot be fully forwarded away, so the pipeline inserts a bubble. Compilers schedule independent instructions into that slot. This is one reason -O2 code interleaves loads with unrelated arithmetic.

Control hazards

A branch's outcome is not known until EX, but the fetch stage has to fetch something on the next cycle. Waiting would cost a bubble on every branch, and roughly one instruction in five or six is a branch.

So the CPU predicts. It fetches down the predicted path speculatively. If the prediction was right, nothing was lost. If it was wrong, the speculatively fetched instructions are flushed and fetch restarts at the correct address. On a deep modern pipeline that misprediction costs roughly 10 to 20 cycles.

  • A branch target buffer remembers where taken branches went, so fetch can redirect before the branch is even decoded.
  • Direction predictors use history: two-bit saturating counters in simple cores, and global-history and TAGE-style predictors in high-end ones, which correctly predict over 95% of branches on typical code.
  • A return stack buffer predicts ret targets by mirroring calls.
/* Data-dependent branch: unpredictable on random input, fast on sorted input */
for (int i = 0; i < n; i++)
    if (v[i] >= 128) sum += v[i];

/* Branchless version: compilers often emit csel / cmov for this */
for (int i = 0; i < n; i++)
    sum += (v[i] >= 128) ? v[i] : 0;

Structural hazards

Two instructions need the same hardware in the same cycle, for example a single memory port shared by instruction fetch and a data load. Separate instruction and data caches (the "modified Harvard" design almost every core uses) exist largely to remove this one.

Why firmware engineers should care

  • Cycle counts in reference manuals are best cases. A Cortex-M4's single-cycle add is single-cycle when its operands are ready and the branch before it was predicted.
  • Flash wait states are pipeline stalls. On microcontrollers, running from flash at high clock speed stalls fetch unless the prefetch buffer or cache hides it, which is why timing-critical ISRs are often placed in RAM.
  • Self-modifying code needs barriers. Instructions already fetched into the pipeline do not see your writes. After writing code to memory, Arm requires cache maintenance followed by dsb and isb; the isb flushes the pipeline so fetch starts again.
  • Speculation leaks. Spectre-class attacks exploit the fact that mispredicted, squashed instructions still leave traces in the caches.
Key takeaway

A pipeline overlaps instructions to approach one per cycle. Data hazards are handled with forwarding and the occasional stall, control hazards with branch prediction and flushes, structural hazards with duplicated hardware. Performance work at the instruction level is mostly about avoiding the stalls.
