Device Tree: How Linux Describes Hardware

A PC can ask its hardware what is connected. Most embedded SoCs cannot. The Device Tree is the file that tells the kernel what hardware exists on this board and where to find it, so one kernel binary can run on many boards.

The problem it solves

On a PC, buses like PCIe and USB are discoverable: the kernel scans them and each device reports its vendor and device ID. But the UART, I²C controller, GPIO block and timers inside an Arm SoC sit at fixed addresses on an internal bus with no way to ask "what are you?".

Before the Device Tree, Arm Linux had a C file per board listing every device by hand. Each board needed its own kernel build. The Device Tree moved that description out of the kernel into data:

Reading a DTS node

The Device Tree is a tree of nodes, each describing one device or bus, with properties as name/value pairs. Here is an I²C controller with a temperature sensor attached:

/ {
    soc {
        #address-cells = <1>;
        #size-cells = <1>;

        i2c1: i2c@40005400 {                     /* node name @ unit address        */
            compatible = "st,stm32f7-i2c";      /* which driver handles this        */
            reg = <0x40005400 0x400>;           /* register base and size           */
            interrupts = <GIC_SPI 31 IRQ_TYPE_LEVEL_HIGH>;
            clocks = <&rcc I2C1_CK>;            /* phandle reference to clock node  */
            #address-cells = <1>;
            #size-cells = <0>;
            status = "okay";                    /* "disabled" = ignore this node     */

            temp@48 {                           /* child: device on the I2C bus      */
                compatible = "ti,tmp102";
                reg = <0x48>;                   /* here: 7-bit I2C address           */
            };
        };
    };
};
PropertyMeaning
compatible"vendor,device" strings, most specific first. The key used to find a driver.
regAddress and size. On a memory-mapped bus, the register window; on I²C, the device address; on SPI, the chip select.
interruptsWhich interrupt line, in the format the parent interrupt controller defines.
clocks, resets, *-gpios, *-supplyReferences (phandles) to other nodes that provide those resources.
status"okay" to use the device. SoC files often disable peripherals; board files enable the ones wired up.
#address-cells, #size-cellsHow many 32-bit numbers children use for address and size in their reg.

A board .dts usually #includes the SoC's .dtsi and overrides only what differs, typically setting status = "okay" and adding child devices.

How a node becomes a bound driver

static const struct of_device_id stm32_i2c_match[] = {
    { .compatible = "st,stm32f7-i2c", .data = &stm32f7_setup },
    { /* sentinel */ }
};
MODULE_DEVICE_TABLE(of, stm32_i2c_match);     /* lets udev autoload the module */

static int stm32_i2c_probe(struct platform_device *pdev)
{
    struct device *dev = &pdev->dev;
    void __iomem *base = devm_platform_ioremap_resource(pdev, 0);   /* from reg */
    int irq = platform_get_irq(pdev, 0);                            /* from interrupts */
    struct clk *clk = devm_clk_get(dev, NULL);                      /* from clocks */
    u32 freq = 100000;

    if (IS_ERR(base)) return PTR_ERR(base);
    if (irq < 0)      return irq;
    if (IS_ERR(clk))  return PTR_ERR(clk);
    of_property_read_u32(dev->of_node, "clock-frequency", &freq);   /* optional */
    /* ... */
    return 0;
}

static struct platform_driver stm32_i2c_driver = {
    .probe  = stm32_i2c_probe,
    .driver = { .name = "stm32f7-i2c", .of_match_table = stm32_i2c_match },
};
module_platform_driver(stm32_i2c_driver);

The driver never contains an address. Everything board-specific comes from the tree, so the same driver serves every board using that SoC.

Bindings: the contract

Which properties a node must have is defined by a binding, a YAML schema in the kernel's Documentation/devicetree/bindings/. Before writing a node, read the binding for its compatible. Validate your tree with:

make ARCH=arm64 dtbs_check          # checks DTS files against the YAML bindings

Inspecting the live tree

The kernel exposes the tree it booted with, which is what actually matters (bootloaders often modify the DTB):

ls /proc/device-tree/soc/                         # same as /sys/firmware/devicetree/base
dtc -I fs -O dts /proc/device-tree > live.dts     # decompile the running tree
cat /sys/bus/platform/devices/40005400.i2c/of_node/compatible
ls -l /sys/bus/platform/devices/40005400.i2c/driver   # which driver bound, if any

When a device never probes

  1. Is the node there and enabled? Check the live tree, not your source file. status = "disabled" in an included .dtsi is the most common cause.
  2. Does the compatible string match exactly? One character off and nothing binds, silently.
  3. Is the driver built? Check the Kconfig option and lsmod or /sys/bus/platform/drivers/.
  4. Is it deferred? If a clock, regulator or GPIO provider is not ready, probe returns -EPROBE_DEFER and is retried later. cat /sys/kernel/debug/devices_deferred lists waiting devices and why.
  5. Did probe fail? Look for the driver's error in dmesg; add dyndbg or temporary dev_err() messages along the probe path.

Overlays

Add-on boards (Raspberry Pi HATs, BeagleBone capes, FPGA bitstreams) use Device Tree overlays: small fragments applied on top of the base DTB by the bootloader, so the base tree does not need editing for every accessory.

Key takeaway

The Device Tree describes non-discoverable hardware as data. Each node's compatible selects a driver, reg, interrupts and phandles supply its resources, and status turns it on. Drivers read those resources in probe() and contain no board-specific addresses.
