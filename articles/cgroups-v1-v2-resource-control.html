cgroups and cgroup v2: Resource Control in Linux, with Examples

A runaway process can eat every CPU core and all the RAM on a machine. Control groups let the kernel put processes in labelled boxes and give each box a budget. They are what makes containers, systemd services and Kubernetes limits work.

The problem cgroups solve

By default, Linux schedules every process as an individual. A build job with 64 compiler processes gets 64 times the CPU of your text editor, and a memory leak in one service can push the whole machine into the OOM killer. Classic tools like nice and ulimit work per process, not per group, and they don't cover memory pressure, disk bandwidth or the number of processes.

A control group (cgroup) is a set of processes the kernel treats as one unit for accounting and limits. You can say "everything in this group together may use at most 2 CPUs and 1 GB of RAM", and every process the group's members start is automatically inside the group too.

The building blocks

  • A hierarchy. cgroups form a tree. Limits on a parent apply to everything below it, so a child can never escape its parent's budget.
  • Membership. Every process is in exactly one cgroup of a hierarchy. Children of a process start in their parent's cgroup.
  • Controllers. Each resource is managed by a kernel controller (historically called a subsystem): cpu, memory, io, pids, cpuset and a few more.
  • A filesystem interface. There is no special system call. A cgroup is a directory under /sys/fs/cgroup; you create one with mkdir, set limits by writing to its files, and move a process in by writing its PID to cgroup.procs.

Underneath, each controller hooks into the relevant part of the kernel: the CPU scheduler checks the group's quota before running its tasks, the page allocator charges every page to the group's memory counter, and the block layer throttles the group's I/O.

cgroup v1 vs cgroup v2

cgroups arrived in Linux 2.6.24 (2008). That first design, now called v1, let each controller have its own separate tree. In practice this turned out messy: a process could be in one group for CPU and an unrelated group for memory, controllers couldn't cooperate, and the rules differed per controller. cgroup v2, stable since Linux 4.5 (2016), replaces this with one unified tree for all controllers.

Check which one your system uses:

stat -fc %T /sys/fs/cgroup     # cgroup2fs = v2 (unified),  tmpfs = v1 (or hybrid)
cat /proc/self/cgroup          # v2: a single line "0::/user.slice/…"

The most useful v2 controls

FileExample valueMeaning
cpu.max50000 100000At most 50 ms of CPU time per 100 ms period: half a CPU. 200000 100000 = 2 CPUs. max 100000 = unlimited.
cpu.weight300Relative share when CPUs are busy. Only matters under contention; idle CPU is never wasted.
cpuset.cpus2-3Pin the group to specific cores.
memory.max512MHard limit. Above it, the kernel reclaims the group's memory; if it can't, the OOM killer kills a process in the group.
memory.high400MSoft limit: above it the group is throttled and reclaimed aggressively, but not killed.
memory.low / memory.min1GProtection: memory under this is kept when other groups need RAM (best effort / guaranteed).
io.max8:0 rbps=10485760 wiops=200Per-device read bandwidth and write IOPS limits (device major:minor).
pids.max64Maximum number of processes and threads: stops fork bombs.
memory.current, cpu.stat, memory.events(read only)Live usage, throttling statistics and OOM counts.

Example: limit a program by hand (cgroup v2)

Run as root on a system with cgroup v2. We create a group, enable the CPU and memory controllers for it, set limits and move a shell inside.

cd /sys/fs/cgroup
cat cgroup.controllers                     # controllers available at the root
echo "+cpu +memory +pids" > cgroup.subtree_control   # let children use them

mkdir demo                                 # create the group
echo "50000 100000" > demo/cpu.max         # 0.5 CPU
echo 100M          > demo/memory.max       # 100 MB hard limit
echo 0             > demo/memory.swap.max  # no swapping around the limit
echo 32            > demo/pids.max

echo $$ > demo/cgroup.procs                # move THIS shell into the group
cat /proc/self/cgroup                      # 0::/demo  -- and every child inherits it

Anything started from that shell now runs inside the limits. Watch the effect:

timeout 5 sh -c 'while :; do :; done' &    # a busy loop
top                                        # shows ~50% CPU, not 100%
cat /sys/fs/cgroup/demo/cpu.stat           # nr_throttled and throttled_usec grow
cat /sys/fs/cgroup/demo/memory.current     # bytes in use right now
cat /sys/fs/cgroup/demo/memory.events      # "oom_kill N" after a limit kill

To remove the group, move the processes out (write their PIDs to the parent's cgroup.procs) and rmdir demo. A group can only be removed when it is empty.

The same experiment on cgroup v1, with real output

v1 uses separate directories per controller and different file names, but the effect is identical. This is real output from a test machine running cgroup v1:

# CPU: 50 ms quota per 100 ms period
mkdir /sys/fs/cgroup/cpu/demo
echo 100000 > /sys/fs/cgroup/cpu/demo/cpu.cfs_period_us
echo 50000  > /sys/fs/cgroup/cpu/demo/cpu.cfs_quota_us
echo $$     > /sys/fs/cgroup/cpu/demo/cgroup.procs
timeout 3 sh -c 'while :; do :; done'
cat /sys/fs/cgroup/cpu/demo/cpu.stat
nr_periods 33
nr_throttled 30
throttled_time 1447883341

In 33 periods of 100 ms the busy loop hit its quota 30 times and was held back for 1.45 seconds out of 3: exactly the 50% we asked for.

For memory, a small program that keeps allocating:

# eat.py: allocate 10 MB at a time, up to 300 MB
b = []
for i in range(1, 31):
    b.append(bytearray(10 * 1024 * 1024))       # zero-filled, so the pages are really used
    print(f"allocated {i * 10} MB", flush=True)
# Memory: 100 MB hard limit, then a program that keeps allocating 10 MB at a time
mkdir /sys/fs/cgroup/memory/demo
echo $((100*1024*1024)) > /sys/fs/cgroup/memory/demo/memory.limit_in_bytes
echo $$ > /sys/fs/cgroup/memory/demo/cgroup.procs
python3 eat.py; echo "exit status: $?"
allocated 80 MB
allocated 90 MB
bash: line 1:   209 Killed                  python3 eat.py
exit status: 137

The program was killed as it crossed 100 MB (exit status 137 = killed by signal 9), and memory.oom_control recorded oom_kill 1. The rest of the machine was unaffected: that is the point. Note that v1 needed a separate directory, and a separate echo $$, for each controller.

You're already using cgroups: systemd

On a systemd machine every service, user session and container is already in its own cgroup. systemd creates the tree (system.slice, user.slice, machine.slice) and exposes the controls as unit properties, so you rarely write the files by hand:

systemd-cgls                              # the cgroup tree with processes
systemd-cgtop                             # live CPU/memory/IO per cgroup

# Run a one-off command in a new cgroup with limits
systemd-run --scope -p CPUQuota=50% -p MemoryMax=100M -p TasksMax=32 stress-ng --cpu 4

# Limit an existing service permanently (writes a drop-in file)
systemctl set-property nginx.service CPUWeight=200 MemoryHigh=1G
systemd propertycgroup v2 file
CPUQuota=50%cpu.max = 50000 100000

TasksMax=64pids.max

Containers are cgroups plus namespaces

A container is not a kernel object. It's an ordinary process tree with two kernel features applied: namespaces decide what the processes can see (their own PID numbers, network, mounts, hostname), and cgroups decide how much they can use. When you run:

docker run --cpus=1.5 --memory=512m --pids-limit=100 nginx

Docker (through runc) creates a cgroup for the container and writes cpu.max = 150000 100000, memory.max = 536870912 and pids.max = 100. Kubernetes CPU and memory limits become the same files on each node, and its requests become weights and memory protection.

Practical tips

  • Prefer memory.high plus memory.max: high throttles and reclaims before max kills, giving the workload a chance to shed memory.
  • Read PSI. memory.pressure and cpu.pressure show the share of time tasks were stalled waiting for that resource. They tell you a limit is too tight long before OOM kills start.
  • Remember page cache counts. File data a group reads is charged to its memory usage. A backup job can hit its memory limit from cache alone; the kernel reclaims that cache first, so this is usually fine.
  • On embedded systems, cgroups are a cheap way to protect a real-time control process from logging, update or UI processes: put the non-critical work in a group with a CPU quota and memory cap.
Key takeaway

A cgroup is a group of processes with shared limits, managed through files under /sys/fs/cgroup. Controllers enforce CPU time, memory, I/O and process counts for the whole group. cgroup v1 gave each controller its own tree; v2 uses one unified tree with consistent files such as cpu.max and memory.max. systemd, Docker and Kubernetes all express their limits by writing those files.
