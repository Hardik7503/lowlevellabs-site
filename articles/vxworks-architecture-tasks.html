VxWorks Architecture: Tasks, RTPs, BSPs and VxBus

VxWorks runs in aircraft, spacecraft, industrial controllers and network equipment. If you are new to it, the hardest part is the vocabulary. Here is how the pieces fit together.

The big picture

VxWorks, from Wind River, is a commercial real-time operating system with deterministic scheduling, a POSIX-compatible API surface and a long history in safety- and mission-critical products. Current releases are VxWorks 7, which is organized as layers you configure into a custom image.

Tasks and the wind scheduler

The unit of execution is a task, roughly a thread with its own stack and register context. The scheduler (historically called the wind kernel) is preemptive and priority-based:

  • Priorities run from 0 (highest) to 255 (lowest). This is the opposite direction from FreeRTOS and POSIX, and a frequent source of porting bugs.
  • The highest-priority ready task always runs. A task becoming ready at a higher priority preempts the current one immediately.
  • Tasks of equal priority run until they block or yield, unless round-robin time slicing is enabled with kernelTimeSlice().
#include <vxWorks.h>
#include <taskLib.h>
#include <stdio.h>

void sensorTask(_Vx_usr_arg_t period)
{
    for (;;) {
        readSensor();
        taskDelay((int)period);          /* ticks, see sysClkRateGet() */
    }
}

void appStart(void)
{
    TASK_ID tid = taskSpawn("tSensor",   /* name, shown in 'i' and debug tools */
                            100,         /* priority: 0 high .. 255 low        */
                            0,           /* options, e.g. VX_FP_TASK            */
                            8192,        /* stack size in bytes                 */
                            (FUNCPTR)sensorTask,
                            10, 0, 0, 0, 0, 0, 0, 0, 0, 0);   /* 10 args */
    if (tid == TASK_ID_ERROR)
        printf("taskSpawn failed\n");
}

By convention task names start with t. In the kernel shell, i lists tasks with priority, state and stack pointer, and checkStack reports stack high-water marks, which is the first thing to check after a mysterious crash.

Kernel tasks versus RTPs

VxWorks offers two places to run application code. Choosing between them is the first architectural decision on a project.

Kernel application (DKM)Real-Time Process (RTP)
ModeSupervisor, same address space as the kernelUser mode, own virtual address space
Fault isolationA bad pointer can take down the whole systemA fault kills the RTP; the kernel and other RTPs keep running
Hardware accessDirect, can call any kernel APIThrough drivers and system calls
OverheadLowest: no system-call boundarySystem calls and MMU context switches
Typical useDrivers, tight control loops, legacy codeApplications, third-party code, anything you want contained
Build outputDownloadable kernel module (.out) or linked into the imageExecutable (.vxe) started with rtpSpawn()

A common split is: drivers and the hardest real-time loops in the kernel, everything else in RTPs.

Inter-task communication

Semaphores

VxWorks has three semaphore types, each created by its own call:

SEM_ID dataReady = semBCreate(SEM_Q_PRIORITY, SEM_EMPTY);   /* binary: signalling   */
SEM_ID slots     = semCCreate(SEM_Q_PRIORITY, 8);           /* counting: resources  */
SEM_ID cfgLock   = semMCreate(SEM_Q_PRIORITY |              /* mutex: exclusion     */
                              SEM_INVERSION_SAFE |          /* priority inheritance */
                              SEM_DELETE_SAFE);             /* holder can't be deleted */

semTake(cfgLock, WAIT_FOREVER);
updateConfig();
semGive(cfgLock);

Use binary semaphores for "something happened", typically given from an ISR. Use mutex semaphores for protecting shared data: they have an owner, support recursive takes by that owner, and can do priority inheritance. See Priority Inversion and How RTOSes Prevent It for why SEM_INVERSION_SAFE matters.

Message queues

typedef struct { uint16_t id; int32_t value; } sample_t;

MSG_Q_ID q = msgQCreate(32, sizeof(sample_t), MSG_Q_PRIORITY);

/* producer */
sample_t s = { .id = 3, .value = adc };
msgQSend(q, (char *)&s, sizeof s, NO_WAIT, MSG_PRI_NORMAL);

/* consumer */
sample_t r;
if (msgQReceive(q, (char *)&r, sizeof r, WAIT_FOREVER) == sizeof r)
    process(&r);

Messages are copied in and out, so producer and consumer never share a buffer. MSG_PRI_URGENT puts a message at the head of the queue.

Interrupts

An ISR runs outside any task context, on the interrupt stack. It must not block, so it cannot take a semaphore or wait on a queue, and must not call anything that might. It can give a binary semaphore or send to a message queue with NO_WAIT, which is the standard way to hand work to a task:

LOCAL void uartIsr(void *arg)
{
    UART_DEV *dev = arg;
    dev->rx = readRxRegister(dev);
    clearInterrupt(dev);
    semGive(dev->rxSem);              /* wake the handling task */
}

In VxWorks 7, drivers normally connect interrupts through VxBus (vxbIntConnect() and vxbIntEnable()) using the interrupt resources described in the Device Tree, rather than the older intConnect() with hard-coded vectors. logMsg() is safe from an ISR; printf() is not.

BSPs, VxBus and the Device Tree

A Board Support Package adapts VxWorks to a specific board: early CPU initialization, the memory map, the system clock, the console and the Device Tree source describing the hardware. Drivers are written against VxBus, the driver framework. In VxWorks 7, VxBus matches drivers to Device Tree nodes by their compatible string, much like Linux does, so the same driver can serve several boards.

uart0: serial@ff000000 {
    compatible = "xlnx,xuartps";
    reg = <0xff000000 0x1000>;
    interrupts = <0 21 4>;
    clock-frequency = <100000000>;
};

Projects: VSB and VIP

In Workbench or the vxprj command-line tool, a VxWorks 7 build has two parts:

  • A VxWorks Source Build (VSB) compiles the OS libraries for your CPU and BSP with the layers and options you choose.
  • A VxWorks Image Project (VIP) links a bootable kernel image from a VSB, selecting components (for example INCLUDE_SHELL or networking) and setting parameters such as the system clock rate.

Application code then goes into DKM or RTP projects built against the VSB.

Habits for people coming from Linux or FreeRTOS

  • Check the priority direction every time you port: 0 is the highest in VxWorks.
  • Kernel tasks share memory with the kernel. Treat every pointer bug as a potential system-wide crash, or move the code into an RTP.
  • Size stacks with checkStack under worst-case load, then add margin. Overflow is a common source of "random" corruption.
  • Use the kernel shell interactively: i, ti tSensor, semShow, msgQShow and memShow answer most "what is the system doing" questions.
  • Capture a System Viewer trace before guessing about timing.
Note

Exact APIs, component names and defaults vary between VxWorks releases and BSPs. Treat this as a map and confirm details against the Wind River documentation for the release you are using.
