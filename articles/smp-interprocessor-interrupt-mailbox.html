SMP Communication: IPIs, Mailboxes and Shared Memory

Cores in a multicore chip need to do two things together: tell each other "something happened", and pass data. Hardware gives you separate tools for each, and robust designs use them together.

11 min read22 Oct 2026 Updated 20 Nov 2026

Two problems, kept apart

When core A has work for core B, it needs to solve:

  1. Notification: get B's attention, even if B is busy or asleep.
  2. Data transfer: get the actual payload to B, correctly ordered and intact.

Interrupts are good at the first and useless for the second. Shared memory is good at the second and has no way to wake anybody. Most designs pair them: put data in shared memory, then send an interrupt.

SMP and AMP

  • SMP (Symmetric Multi-Processing): identical cores run one operating system, which schedules threads on any core. Linux on a quad-core Cortex-A53 is SMP.
  • AMP (Asymmetric Multi-Processing): different cores run different software, for example Linux on Cortex-A cores and an RTOS or bare-metal firmware on a Cortex-M or R core in the same SoC (i.MX8, STM32MP1, Zynq).

The mechanisms below apply to both, but AMP needs more care because the two sides do not share an OS, locks or even a cache.

Inter-processor interrupts (IPIs)

An IPI is an interrupt one core sends to another. On Arm, the GIC interrupt controller provides Software Generated Interrupts (SGIs), IDs 0 to 15: a core writes a register naming the target cores and the SGI number, and those cores take an interrupt. On x86 the local APIC does the same job.

Linux uses IPIs constantly in SMP: to reschedule a thread on another CPU, to run a function on other CPUs (smp_call_function_single()), and for TLB shootdowns. You can watch the counts in /proc/interrupts under rows such as IPI0: Rescheduling interrupts.

/* Linux kernel: run a function on CPU 2 and wait for it to finish */
static void read_counter(void *info)
{
    *(u64 *)info = read_local_counter();      /* runs on CPU 2, in IRQ context */
}

u64 val;
smp_call_function_single(2, read_counter, &val, 1 /* wait */);

Hardware mailboxes

A mailbox is a peripheral built for core-to-core messages, common in heterogeneous SoCs. It typically has a few message registers or a small FIFO and raises an interrupt on the receiving side when a message arrives.

  • Good for short messages: a command code, an index into a shared buffer, "ring 3 has new data".
  • Status bits show whether the receiver has read the last message, which gives simple flow control.
  • Linux exposes them through the mailbox framework (mbox_send_message()), and remoteproc/RPMsg uses them to kick the other processor.

Shared memory

For real payloads, both sides read and write an agreed region of RAM. The classic structure is a single-producer, single-consumer ring buffer: one side only writes head, the other only writes tail, so no lock is needed.

#include <stdatomic.h>
#include <stdint.h>

#define RING_SIZE 64                      /* power of two */

struct msg { uint32_t cmd; uint32_t arg; };

struct ring {
    _Atomic uint32_t head;                /* written only by producer */
    _Atomic uint32_t tail;                /* written only by consumer */
    struct msg slot[RING_SIZE];
};

int ring_put(struct ring *r, struct msg m)          /* producer core */
{
    uint32_t h = atomic_load_explicit(&r->head, memory_order_relaxed);
    uint32_t t = atomic_load_explicit(&r->tail, memory_order_acquire);
    if (h - t == RING_SIZE)
        return -1;                                   /* full */
    r->slot[h % RING_SIZE] = m;                      /* 1. write the data      */
    atomic_store_explicit(&r->head, h + 1, memory_order_release);  /* 2. publish */
    return 0;
}

int ring_get(struct ring *r, struct msg *out)       /* consumer core */
{
    uint32_t t = atomic_load_explicit(&r->tail, memory_order_relaxed);
    uint32_t h = atomic_load_explicit(&r->head, memory_order_acquire);
    if (h == t)
        return -1;                                   /* empty */
    *out = r->slot[t % RING_SIZE];
    atomic_store_explicit(&r->tail, t + 1, memory_order_release);
    return 0;
}

The release store on head guarantees the slot data is visible before the new index; the acquire load on the other side guarantees the consumer reads the slot only after seeing the index. Without them, a weakly ordered CPU can expose the index first and the consumer reads garbage. Free-running unsigned indexes make full and empty unambiguous and wrap correctly.

AMP extras: caches and ownership

  • A Cortex-M side may not be cache-coherent with the Cortex-A side. Place the shared region in non-cacheable memory, or do explicit cache maintenance as with DMA buffers.
  • Agree on the layout precisely: fixed-width types, explicit alignment, a version field, and a magic number so each side can detect that the other is initialized.
  • Reserve the region in both memory maps (a reserved-memory node in the Linux Device Tree) so neither OS hands it out for something else.

Putting it together

One more detail: the receiver should drain everything in the ring each time it wakes, and the sender can skip the kick when the ring was already non-empty. That batches notifications and avoids an interrupt per message under load.

Key takeaway

IPIs and mailboxes notify; shared memory carries data. A single-producer single-consumer ring with release/acquire ordering moves data without locks, and a single interrupt per batch wakes the consumer. In AMP systems, also handle cache coherence, memory reservation and a precise shared layout.
