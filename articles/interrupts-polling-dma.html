Interrupts vs. Polling vs. DMA

A peripheral finishes something: a byte arrives, a conversion completes, a buffer is sent. Software has to notice and move the data. There are three basic ways to do that, and choosing well decides whether your CPU is busy, idle or asleep.

An analogy first

You are waiting for a pizza delivery.

  • Polling: you walk to the door every minute to check. Simple, but you get nothing else done, and if you check too rarely the pizza goes cold.
  • Interrupt: you get on with your work and the doorbell rings when it arrives. You stop, collect the pizza, and go back to work.
  • DMA: you hire someone to receive all twenty pizzas for a party and put them on the table. They ring you once, when the whole order is done.

Hardware works the same way. The "door" is a status register, the "doorbell" is an interrupt line, and the "helper" is the DMA controller.

Polling

The CPU repeatedly reads a status register until a flag says the device is ready, then does the transfer itself.

/* Send a string over a UART by polling */
void uart_puts(const char *s)
{
    while (*s) {
        while (!(UART->SR & SR_TXE)) { }   /* spin until the TX register is empty */
        UART->DR = *s++;
    }
}

Good: trivial to write, no concurrency, and the lowest possible latency when the CPU has nothing else to do, because the response starts on the very next loop iteration. Bad: the CPU is 100% busy while waiting. At 115200 baud a byte takes about 87 µs; a 72 MHz CPU wastes roughly 6000 cycles per character.

Polling is the right choice in bootloaders, in early bring-up, in panic and crash handlers (where interrupts may be unusable), and for events that are known to complete within a few cycles.

Interrupts

The device raises a signal when it needs attention. The CPU finishes its current instruction, saves its state, and jumps to an interrupt service routine (ISR). When the ISR returns, the interrupted code continues as if nothing happened.

static volatile uint8_t  rx_buf[64];
static volatile uint32_t rx_head;

void USART1_IRQHandler(void)            /* name comes from the vector table */
{
    if (UART->SR & SR_RXNE) {           /* which event? check the cause */
        rx_buf[rx_head++ % 64] = (uint8_t)UART->DR;   /* reading DR clears RXNE */
    }
}

Good: the CPU can run other code or sleep, and response time is short and predictable. Bad: every event has a fixed overhead (saving registers, entering and leaving the ISR), concurrency bugs appear because the ISR can run between any two instructions of the main code, and at high event rates the overhead dominates. A 10 Gb/s network card receiving small packets would interrupt millions of times a second and do nothing else; that problem has a name, interrupt storm or livelock.

Rules for ISRs

Keep them short. Acknowledge or clear the interrupt source, or it will fire again immediately. Don't block, don't call printf, and hand longer work to a task or thread. Variables shared with the ISR need volatile and, if wider than one word, a critical section.

DMA

A Direct Memory Access controller is a small engine that copies data between a peripheral and memory, or between two memory regions, without the CPU touching each byte. The CPU programs it once (source, destination, length, trigger), starts it, and gets one interrupt when the whole block is done.

void uart_rx_start(void)
{
    DMA1_CH5->CPAR  = (uint32_t)&UART->DR;   /* source: peripheral data register */
    DMA1_CH5->CMAR  = (uint32_t)rx_buf;      /* destination: memory              */
    DMA1_CH5->CNDTR = sizeof rx_buf;         /* number of transfers              */
    DMA1_CH5->CCR   = DMA_MINC | DMA_TCIE | DMA_EN;   /* increment mem, IRQ on done */
    UART->CR3      |= UART_DMAR;             /* let the UART request DMA          */
}

(Register names follow an STM32F1-style DMA. Other controllers differ in detail but take the same four pieces of information.)

Good: high throughput at almost no CPU cost; the CPU can even sleep during the transfer. Bad: setup cost makes it pointless for a few bytes, there are a limited number of channels, and it brings memory-system problems: the CPU's cache may hold stale data (see DMA and Cache Coherency), and buffers must stay valid and untouched while the transfer runs.

Choosing

PollingInterruptsDMA
CPU cost while waiting100%NoneNone
CPU cost per byteCopy loopInterrupt overhead + copyNone
Setup costNoneSmallLarger
Best forVery short waits, boot code, crash pathsSporadic events, low data ratesBulk data: audio, ADC streams, network, storage
ComplexityLowestConcurrency with ISRBuffers, caches, error handling

Real drivers combine all three

  • UART receive: DMA into a circular buffer, plus an "idle line" interrupt so a short message is processed without waiting for the buffer to fill.
  • Network cards: DMA rings for packets; an interrupt announces new packets; then the driver switches interrupts off and polls the ring until it is empty. Linux calls this NAPI. It gives interrupt-like latency at low load and polling-like efficiency at high load.
  • Storage (NVMe): DMA for data, completion queues in memory, and interrupts or polling for completions depending on the latency target.
Key takeaway

Polling spends CPU time to get simplicity. Interrupts let the CPU work or sleep until an event, at a small cost per event. DMA moves blocks of data without the CPU and interrupts once per block. Use polling for tiny waits, interrupts for sporadic events, DMA for streams, and combine them when load varies.
