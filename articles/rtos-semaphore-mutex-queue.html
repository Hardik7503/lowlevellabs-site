Semaphore, Mutex or Queue? Choosing RTOS Primitives

Every RTOS gives you the same small toolbox. Most synchronization bugs come from picking the wrong tool, not from using the right one badly.

9 min read20 Nov 2026

Three different jobs

RTOS primitives solve three distinct problems. Name the problem first, and the primitive follows.

Binary semaphore: "it happened"

A binary semaphore is a flag with a wait queue. One side gives it, the other takes it and blocks until it is available. It has no owner: the giver and the taker are usually different contexts. The canonical use is deferring work from an interrupt to a task.

static SemaphoreHandle_t rxDone;

void DMA1_Stream5_IRQHandler(void)
{
    BaseType_t woken = pdFALSE;
    clear_dma_flags();
    xSemaphoreGiveFromISR(rxDone, &woken);
    portYIELD_FROM_ISR(woken);     /* switch now if a higher-priority task woke */
}

void rxTask(void *arg)
{
    for (;;) {
        if (xSemaphoreTake(rxDone, pdMS_TO_TICKS(100)) == pdTRUE)
            parse_frame();
        else
            report_timeout();
    }
}

/* setup: rxDone = xSemaphoreCreateBinary(); */

If the event fires twice before the task runs, the second give is lost: a binary semaphore counts to one. If you must not lose events, use a counting semaphore or a queue.

Counting semaphore: "how many are available"

A counting semaphore holds a count. Take decrements it, blocking at zero; give increments it. Use it to count events that may arrive in bursts, or to guard a pool of identical resources such as eight DMA descriptors.

SemaphoreHandle_t freeBufs = xSemaphoreCreateCounting(8, 8);   /* max, initial */

xSemaphoreTake(freeBufs, portMAX_DELAY);   /* reserve one buffer  */
/* ... use a buffer from the pool ... */
xSemaphoreGive(freeBufs);                  /* return it           */

The semaphore only counts. You still need a way to pick which buffer, protected by its own lock or by a queue of free buffer pointers.

Mutex: "only one at a time"

A mutex looks like a binary semaphore but adds ownership: only the task that took it may give it back. Ownership is what enables priority inheritance (see priority inversion), recursive locking and error checking.

static SemaphoreHandle_t i2cLock;    /* = xSemaphoreCreateMutex(); */

int sensor_read(uint8_t reg, uint8_t *val)
{
    if (xSemaphoreTake(i2cLock, pdMS_TO_TICKS(20)) != pdTRUE)
        return -ETIMEDOUT;
    int rc = i2c_xfer(SENSOR_ADDR, &reg, 1, val, 1);
    xSemaphoreGive(i2cLock);
    return rc;
}
Pitfall: mutexes in interrupts

Never take or give a mutex from an ISR. An ISR is not a task, so it cannot own anything, cannot be boosted and must never block. FreeRTOS does not provide FromISR variants for mutexes for exactly this reason.

Queue: "here is the data"

A queue copies fixed-size items into a ring buffer owned by the kernel. It synchronizes and transfers data in one step: the consumer blocks until an item arrives, and the producer blocks (or fails) when the queue is full. Because data is copied, producer and consumer never share memory, so no extra lock is needed.

typedef struct { uint32_t ts; int16_t x, y, z; } accel_t;
QueueHandle_t accelQ = xQueueCreate(16, sizeof(accel_t));

/* producer task (from an ISR use xQueueSendFromISR) */
accel_t s = read_accel();
if (xQueueSend(accelQ, &s, 0) != pdTRUE)
    dropped++;                      /* queue full: count it, don't block */

/* consumer */
accel_t r;
while (xQueueReceive(accelQ, &r, portMAX_DELAY) == pdTRUE)
    filter_update(&r);

For large payloads, queue a pointer to a buffer from a pool instead of the payload itself, and make the ownership hand-off explicit: whoever holds the pointer owns the buffer.

Task notifications: the lightweight option

FreeRTOS also gives every task a built-in notification value. xTaskNotifyGive() and ulTaskNotifyTake() behave like a counting semaphore aimed at one specific task, with less RAM and faster execution than a separate semaphore object. They are a good default for "ISR wakes exactly one known task". Other RTOSes have equivalents, such as event flags in VxWorks and ThreadX.

Rules that prevent most bugs

  • Always use timeouts during development, and log when they expire. portMAX_DELAY turns a bug into a silent hang.
  • Only the FromISR APIs from interrupts, and respect configMAX_SYSCALL_INTERRUPT_PRIORITY on Cortex-M: ISRs above that priority must not call any RTOS API.
  • Lock in a fixed global order when a task needs two mutexes, or deadlock is only a matter of timing.
  • Keep the locked region small. Copy data out under the lock, process it after releasing.
Key takeaway

Semaphores signal, mutexes protect, queues move data. Choose by the job, use the ISR-safe variants from interrupts, and never use a semaphore where you need an owner.
