What Happens When a Linux Driver Probes?

In Linux you never call your driver's setup function yourself. You register the driver, the kernel registers devices, and a matchmaker in the middle calls your probe() when the two fit. Once you see that model, every driver looks familiar.

Three objects and a matchmaker

The Linux driver model is built on three kinds of objects:

  • A bus (struct bus_type): platform, PCI, USB, I²C, SPI. It knows how to compare a device with a driver.
  • A device (struct device): one piece of hardware the kernel knows exists, with its resources. Created by bus enumeration (PCI, USB) or from the Device Tree or ACPI.
  • A driver (struct device_driver): code that can operate a kind of device, with a table of the IDs it supports.

The driver core keeps a list of devices and drivers per bus. Whenever either side is added, it tries to pair them using the bus's match() function. On a match, it calls the driver's probe().

How matching works

Each bus decides what "match" means, but the idea is always an ID table in the driver:

BusDevice identified byDriver table
Platform (Device Tree)compatible stringof_device_id[]
Platform (ACPI)ACPI HID such as "PRP0001"acpi_device_id[]
PCIVendor and device IDpci_device_id[]
USBVendor, product, classusb_device_id[]
I²C / SPIcompatible string, or nameof_device_id[], i2c_device_id[]

MODULE_DEVICE_TABLE() exports that table into the module's metadata, so udev can load the right module automatically when a matching device appears.

What probe() should do

Probe's job: take this device from "known to exist" to "fully working and registered with its subsystem". A typical order:

struct tmp_dev {
    struct i2c_client *client;
    struct regmap     *map;
};

static int tmp_probe(struct i2c_client *client)
{
    struct device *dev = &client->dev;
    struct tmp_dev *td;
    struct regulator *vdd;
    unsigned int id;
    int ret;

    td = devm_kzalloc(dev, sizeof(*td), GFP_KERNEL);              /* 1 */
    if (!td)
        return -ENOMEM;
    td->client = client;

    vdd = devm_regulator_get(dev, "vdd");                          /* 2 */
    if (IS_ERR(vdd))
        return dev_err_probe(dev, PTR_ERR(vdd), "no vdd supply\n");

    td->map = devm_regmap_init_i2c(client, &tmp_regmap_cfg);
    if (IS_ERR(td->map))
        return PTR_ERR(td->map);

    ret = regmap_read(td->map, REG_DEVICE_ID, &id);                /* 3 */
    if (ret)
        return dev_err_probe(dev, ret, "device not responding\n");
    if (id != EXPECTED_ID)
        return dev_err_probe(dev, -ENODEV, "unexpected id 0x%x\n", id);

    i2c_set_clientdata(client, td);
    return devm_hwmon_device_register_with_info(dev, "tmp", td,    /* 5 */
                                                &tmp_chip_info, NULL);
}

(Regulator enabling and the IRQ are left out to keep the example short; they follow the same devm_ pattern.)

devm_: cleanup for free

Every resource acquired in probe must be released when the device goes away, and also when probe fails halfway. Writing that cleanup by hand with goto ladders is error-prone. Managed resources (devm_* functions) are recorded against the device and released automatically, in reverse order, when probe fails or the driver unbinds. Prefer them everywhere they exist.

Pitfall: devm and IRQ ordering

A devm_request_irq() handler is freed after remove() runs. If remove() shuts the hardware down or frees data the handler uses, a late interrupt can crash. Disable the device's interrupts in remove() first.

Deferred probing

Probe may need something that isn't ready yet: a clock from a driver that hasn't probed, a regulator on a PMIC still being set up. Returning -EPROBE_DEFER tells the driver core "try me again later". It retries deferred devices whenever another driver successfully binds. dev_err_probe() handles this nicely: for -EPROBE_DEFER it records the reason quietly instead of printing an error.

cat /sys/kernel/debug/devices_deferred      # which devices are waiting, and why

remove() and the rest of the lifecycle

  • remove() runs on unbind, module unload or hot-unplug. Undo what probe did that devm doesn't cover: stop the hardware, cancel work items, unregister anything registered manually.
  • shutdown() runs at reboot to leave hardware quiet.
  • Power management callbacks (suspend/resume, runtime PM) save and restore state around low-power modes.

You can trigger unbind and bind by hand to test remove paths:

echo 1-0048 | sudo tee /sys/bus/i2c/drivers/tmp102/unbind
echo 1-0048 | sudo tee /sys/bus/i2c/drivers/tmp102/bind

Rules of thumb

  • Probe can run at any time, on any CPU, possibly in parallel with other probes. Don't rely on global state or probe order.
  • Return a meaningful negative error code; -ENODEV means "not my device", and the core will try other drivers.
  • Never busy-wait for seconds in probe. If hardware takes long to start, do it asynchronously or set PROBE_PREFER_ASYNCHRONOUS.
  • Check the ID register if the device has one. It catches wiring and address mistakes immediately.
Key takeaway

Drivers and devices register independently on a bus; the driver core matches them by ID and calls probe(). Probe allocates state, acquires resources (preferably with devm_), brings the hardware up, and registers with its subsystem last. If a dependency is missing, it returns -EPROBE_DEFER and is retried.
