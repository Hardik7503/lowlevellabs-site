MESI Cache Coherence Explained

Every core in a multicore CPU has its own cache. If two cores cache the same variable and one changes it, what does the other see? Cache coherence protocols answer that, and MESI is the classic one.

The problem

A cache keeps copies of recently used memory close to the core, because RAM is around a hundred times slower. Caches store memory in fixed-size chunks called cache lines, typically 64 bytes.

With one core, a cached copy can never be "wrong": only that core changes memory. With two cores, each with a private cache, this can happen:

  1. Core 0 reads x = 0 into its cache.
  2. Core 1 reads x = 0 into its cache.
  3. Core 0 writes x = 1 into its own cache.
  4. Core 1 reads x again, hits in its cache, and still sees 0. Forever.

A coherence protocol prevents step 4. Its rule: at any moment a line can have many readers or one writer, never both. Before a core writes, every other copy must be invalidated.

The four MESI states

Each cache line in each core's cache is tagged with one of four states:

StateMeaningOther caches have it?Matches RAM?Can write without asking?
ModifiedI changed it; I hold the only valid copyNoNo (dirty)Yes
ExclusiveI have the only copy and haven't changed itNoYesYes (silently becomes M)
SharedOthers may have copies tooMaybeYesNo: must invalidate others first
InvalidThis slot holds nothing usable——No: must fetch first

The Exclusive state is the clever part. A core that reads data nobody else has can later write it without any bus traffic, which is very common for private data such as a thread's stack.

The transition table

Every state change is caused by one of four events: this core reads or writes the line (local), or another core reads or writes it (remote, seen by snooping). This table is the whole protocol:

Current stateLocal readLocal writeRemote readRemote write
MM (hit)M (hit)S, supply data and write backI, supply data first
EE (hit)M, silently: no bus trafficSI
SS (hit)M, after invalidating other copiesSI
IE if no one else has it, otherwise SM, via read-for-ownershipII

Read the columns as rules: a local write always ends in M; a remote write always ends in I; a remote read always downgrades M and E to S.

How caches find out: snooping and directories

  • Snooping: every cache watches (snoops) the shared bus or interconnect for other cores' requests and reacts to ones that hit its lines. Simple and fast with a few cores, but broadcast traffic grows with core count.
  • Directories: a central structure records which cores hold each line, so invalidations go only to those cores. Used in large many-core and multi-socket systems.

Real processors use extended protocols: MOESI (AMD, many Arm systems) adds an Owned state so a dirty line can be shared without writing it back first, and MESIF (Intel) adds Forward so exactly one sharer answers requests. The core idea is unchanged.

False sharing: a performance trap

Coherence works on whole cache lines, not variables. If two threads write two different variables that happen to share a 64-byte line, the line bounces between cores on every write, even though the threads never share data.

struct counters {
    long a;     /* written only by thread 0 */
    long b;     /* written only by thread 1 -- same cache line as a! */
};

/* Fix: give each its own line */
struct counters_padded {
    _Alignas(64) long a;
    _Alignas(64) long b;
};

False sharing can make a "parallel" loop slower than a single-threaded one. In the Linux kernel you will see ____cacheline_aligned_in_smp on per-CPU fields for this reason.

Coherence is not consistency

MESI guarantees that all cores agree on the order of writes to one cache line. It does not guarantee the order in which a core's writes to different addresses become visible to others. That is the memory consistency model, and CPUs relax it for speed using store buffers and out-of-order execution.

/* core 0 */                 /* core 1 */
data  = 42;                  while (ready == 0) { }
ready = 1;                   use(data);          /* may still see old data on Arm */

On a weakly ordered CPU like Arm or RISC-V, core 1 can see ready == 1 before data == 42, on a perfectly coherent machine. The fix is a release/acquire pair (C11 atomic_store_explicit(&ready, 1, memory_order_release) and a matching acquire load) or the kernel's smp_store_release()/smp_load_acquire(). x86 is more strongly ordered and happens to keep this particular pattern working, which is why such bugs often appear only after porting to Arm.

What about DMA?

Coherence protocols keep CPU caches consistent with each other. A DMA device may or may not take part. On many embedded SoCs it does not, so drivers must clean and invalidate caches around DMA. See DMA and Cache Coherency.

Key takeaway

MESI tags each cache line Modified, Exclusive, Shared or Invalid so that a line has either many readers or one writer. Writes to shared lines cost invalidations, unrelated data sharing a line causes false sharing, and coherence alone does not order accesses to different addresses: that needs barriers or acquire/release atomics.
