DMA and Cache Coherency

The CPU looks at memory through its cache. A DMA device often looks at RAM directly. When the two views disagree, you get corrupted packets, stale sensor data and bugs that disappear when you add a printf.

Two views of the same memory

The CPU almost never reads or writes RAM directly. It works on copies in its data cache, and the cache writes changes back to RAM later, when it needs the space. That is invisible to software running on the CPU, because every CPU access goes through the same cache.

A DMA device (Ethernet controller, SD host, camera interface) reads and writes RAM on its own (see Interrupts vs Polling vs DMA). On many embedded SoCs, that traffic does not go through the CPU's cache, and the cache is not told about it. Now there are two copies of the data that can disagree.

Two cache operations you need

  • Clean (also called flush or write back): write any modified cache lines for an address range out to RAM. The cache keeps its copy. Use it before a device reads memory.
  • Invalidate: throw away the cache's copy of an address range, without writing it back. The next CPU read fetches fresh data from RAM. Use it before the CPU reads memory a device wrote.

Both work on whole cache lines (commonly 64 bytes), which matters later.

Direction 1: CPU → device (transmit)

Direction 2: device → CPU (receive)

Why invalidate before and after? Before, because a dirty line evicted during the transfer would overwrite what the device wrote. After, because the CPU may have speculatively loaded the buffer into its cache while the transfer was running.

The cache-line sharing trap

Invalidate works on whole lines. If a receive buffer starts or ends in the middle of a line that also holds an unrelated variable, invalidating the buffer also throws away any pending update to that variable.

/* Bare metal: give DMA buffers their own cache lines */
#define CACHE_LINE 64
static uint8_t rx_buf[1536] __attribute__((aligned(CACHE_LINE)));   /* 1536 = 24 lines */

Bare-metal example (Cortex-M7)

/* CMSIS cache maintenance on a Cortex-M7 with D-cache enabled */
void eth_send(const void *frame, size_t len)
{
    memcpy(tx_buf, frame, len);
    SCB_CleanDCache_by_Addr((uint32_t *)tx_buf, (int32_t)len);     /* CPU → RAM */
    __DSB();                                                        /* finish before doorbell */
    ETH_DMA->TX_POLL = 1;
}

void eth_rx_done_irq(void)
{
    SCB_InvalidateDCache_by_Addr((uint32_t *)rx_buf, sizeof rx_buf); /* drop stale lines */
    process_frame(rx_buf);
}

An alternative on microcontrollers is to place DMA buffers in a region the MPU marks non-cacheable. Then no maintenance is needed, at the cost of slower CPU access to that memory.

In Linux: use the DMA API

Linux drivers never call cache instructions directly. The DMA API knows whether the device is coherent and does the right thing, including bounce buffers and IOMMU mappings:

/* Streaming mapping: one transfer, CPU gives buffer ownership to the device */
dma_addr_t dma = dma_map_single(dev, buf, len, DMA_TO_DEVICE);   /* cleans cache  */
if (dma_mapping_error(dev, dma))
    return -ENOMEM;
start_device_tx(dma, len);
/* ... completion interrupt ... */
dma_unmap_single(dev, dma, len, DMA_TO_DEVICE);

/* Receive buffer reused many times */
dma_sync_single_for_cpu(dev, dma, len, DMA_FROM_DEVICE);    /* invalidate, CPU may read */
consume(buf);
dma_sync_single_for_device(dev, dma, len, DMA_FROM_DEVICE); /* give back to device */

/* Coherent (consistent) mapping: long-lived descriptor rings */
void *ring = dma_alloc_coherent(dev, size, &ring_dma, GFP_KERNEL);

The rule of ownership: between map (or sync_for_device) and unmap (or sync_for_cpu), the device owns the buffer and the CPU must not touch it.

Mapping typeUse forCost
Streaming (dma_map_single)Data buffers, packets, blocksCache maintenance per transfer; CPU access to buffer is fully cached
Coherent (dma_alloc_coherent)Descriptor rings, mailboxes shared continuouslyOften uncached on non-coherent systems: slower CPU access

Hardware-coherent DMA

Some systems make DMA coherent: device traffic goes through the interconnect, which snoops CPU caches (x86 PCIe, Arm systems with ACE-Lite or CHI interconnects). In Linux the Device Tree property dma-coherent tells the kernel. Cache maintenance is then unnecessary, but barriers for ordering still are, and the same driver code using the DMA API works on both kinds of system.

Symptoms that point to this bug

  • Received data is correct except for occasional 32- or 64-byte chunks of old content.
  • The first packet after boot is fine; later ones contain fragments of earlier packets.
  • The bug disappears when you add a printf, enable debug logging or disable the data cache.
Key takeaway

On non-coherent systems, clean the cache before a device reads memory and invalidate it before the CPU reads what a device wrote. Align buffers to cache lines. In Linux, use the DMA API, respect buffer ownership, and let it decide what maintenance the platform needs.
