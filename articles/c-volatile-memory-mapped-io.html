volatile and Memory-Mapped I/O in Embedded C

A peripheral register looks like ordinary memory to C, but it behaves nothing like it. volatile is the one keyword that tells the compiler so, and it is also one of the most misunderstood.

9 min read20 Nov 2026

Registers are not memory

On most microcontrollers and SoCs, peripheral registers are memory-mapped: a UART status register might live at physical address 0x4000_4400, and the CPU reads it with an ordinary load instruction. To the C compiler, that address is just an object it can read and write.

But a register is not passive storage. Reading a status register reports the hardware's state right now, which can change between two reads without any instruction running. Reading a data register can pop a byte from a FIFO. Writing a register can start a DMA transfer. Every access is an event.

The compiler optimizes under the assumption that memory only changes when the program changes it. That assumption is exactly wrong for hardware.

The bug: a loop that never exits

Here is a polling loop that waits for the UART's transmit-empty flag, written without volatile:

#define UART_SR   (*(uint32_t *)0x40004400u)   /* status register */
#define UART_DR   (*(uint32_t *)0x40004404u)   /* data register   */
#define SR_TXE    (1u << 7)

void uart_putc(char c)
{
    while ((UART_SR & SR_TXE) == 0)
        ;                       /* wait for space in the TX FIFO */
    UART_DR = (uint32_t)c;
}

At -O0 this often works. At -O2, the compiler is entitled to reason: nothing inside the loop writes UART_SR, so its value cannot change, so load it once. The generated code becomes "load once, then spin forever if the bit was clear", which is a hang that only appears in release builds.

uart_putc:
    ldr   r3, =0x40004400
    ldr   r3, [r3]          @ loaded ONCE
    tst   r3, #128
    beq   .Lspin
    ...
.Lspin:
    b     .Lspin            @ infinite loop, register never re-read

What volatile guarantees

Qualifying the object as volatile tells the compiler that every access is an observable side effect. In practice, for each read or write of a volatile object in the source, the compiler must:

  • Perform the access. It cannot drop a read because it "knows" the value, and cannot drop a write because a later write overwrites it.
  • Not invent extra accesses and not merge two accesses into one.
  • Keep volatile accesses in program order relative to each other.
#define UART_SR   (*(volatile uint32_t *)0x40004400u)
#define UART_DR   (*(volatile uint32_t *)0x40004404u)

Now every iteration emits a fresh ldr, and the loop exits when the hardware sets the bit.

The idiomatic form: a register struct

Vendor headers (CMSIS, for example) describe a peripheral as a struct overlaid on its base address. The layout mirrors the register map in the reference manual:

#include <stddef.h>
#include <stdint.h>

#define SR_TXE  (1u << 7)

typedef struct {
    volatile uint32_t SR;      /* 0x00 status            */
    volatile uint32_t DR;      /* 0x04 data              */
    volatile uint32_t BRR;     /* 0x08 baud rate         */
    volatile uint32_t CR1;     /* 0x0C control 1         */
} uart_regs_t;

#define UART1  ((uart_regs_t *)0x40004400u)

_Static_assert(offsetof(uart_regs_t, CR1) == 0x0C, "register map mismatch");

void uart_putc(char c)
{
    while ((UART1->SR & SR_TXE) == 0) { }
    UART1->DR = (uint8_t)c;
}

The _Static_assert catches a missing or mis-sized field at compile time, which is the most common register-map bug. Mark read-only registers const volatile so an accidental write fails to compile.

Read side effects: why "harmless" reads are not

Some registers change state when read. On many UARTs, reading the data register removes a byte from the receive FIFO; on some timers, reading a status register clears pending flags. That has two consequences:

  • A debugger's memory view that refreshes a peripheral region can silently consume data. If RX bytes "disappear" only while debugging, check your watch windows.
  • Code like if (UART1->DR == 'q' || UART1->DR == 'Q') performs two reads and consumes two bytes. Read once into a local variable, then test the local.

What volatile does not do

This is where most real bugs live. volatile constrains the compiler. It says nothing to the CPU's memory system or to other cores.

ProblemDoes volatile solve it?What to use instead
Compiler caching a register in a CPU registerYes—
Read-modify-write racing with an ISRNo. reg |= x is still load, OR, store.Disable interrupts around it, or use set/clear registers
Sharing a counter between two coresNo. No atomicity, no inter-core ordering.C11 _Atomic, RTOS primitives, kernel atomics
CPU reordering a buffer write before a "start DMA" register writeNo. Volatile only orders volatile accesses, and the CPU may still reorder.A memory barrier (__DMB(), dma_wmb())
Stale data in the data cache after DMANoCache maintenance or the OS DMA API
Pitfall: the descriptor-then-doorbell race

You fill a DMA descriptor in normal RAM, then write the device's "go" register. The doorbell write is volatile; the descriptor writes are not. Both the compiler and an out-of-order CPU may make the doorbell visible to the device before the descriptor. Put a write barrier between them, and on non-coherent systems clean the cache lines first.

Sharing variables with an interrupt handler

A flag set in an ISR and polled in the main loop must be volatile, for the same reason as a status register: from the main loop's point of view it changes "by itself".

static volatile bool    rx_ready;
static volatile uint8_t rx_byte;

void USART1_IRQHandler(void)
{
    rx_byte  = (uint8_t)UART1->DR;   /* reading DR also clears RXNE */
    rx_ready = true;
}

int main(void)
{
    for (;;) {
        if (rx_ready) {
            uint8_t b = rx_byte;     /* copy before clearing the flag */
            rx_ready = false;
            handle(b);
        }
    }
}

This is safe on a single core because a 32-bit aligned access is atomic on the architectures you are likely to use, and there is one writer per field. As soon as the shared state is wider than one word, or both sides modify it, you need a critical section. volatile alone will not give you one.

In the Linux kernel: don't use volatile

Kernel code does not declare register pointers volatile. Instead, it maps the region with ioremap() or devm_platform_ioremap_resource() and uses accessors:

u32 sr = readl(base + UART_SR);      /* includes the ordering guarantees I/O needs */
writel(c, base + UART_DR);
writel_relaxed(val, base + REG);     /* no barrier, for hot paths you reason about */

The accessors handle volatility, endianness and the barriers each architecture needs. The kernel's documentation ("Why the volatile type class should not be used") explains that volatile on shared data usually hides a missing lock rather than fixing it.

Key takeaway

Use volatile for memory-mapped registers and for single-word flags shared with an ISR. Never rely on it for atomicity, for ordering between CPU and device, or for ordering between cores. Those need critical sections, atomics and barriers.
