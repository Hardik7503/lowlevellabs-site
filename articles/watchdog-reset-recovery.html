Watchdogs and Fault Recovery in Embedded Systems

A watchdog can recover a system that stops making progress, but a watchdog that is fed unconditionally may hide failures. Reliable designs monitor meaningful progress and define what the system should do after a timeout.

What a watchdog detects

A hardware watchdog resets the system if software fails to service it within a configured interval. It is useful when the CPU or software becomes stuck, but it cannot detect every incorrect result. A live system can still be producing wrong data.

Feed progress, not just execution

If a periodic timer feeds the watchdog regardless of subsystem health, a deadlocked worker may go unnoticed. A stronger design requires critical tasks to publish progress indicators, and a supervisor checks that each required component has advanced within its deadline before refreshing the watchdog.

Timeout selection

Choose the timeout using worst-case scheduling delay, legitimate long operations, startup behavior, and recovery requirements. Too short creates nuisance resets; too long delays recovery. Document whether a timeout causes a local restart, subsystem reset, controlled shutdown, or full-board reset.

Record evidence before reset

Where hardware permits, preserve a reset reason, fault code, heartbeat counters, and a compact crash record in retained memory. Ensure the record itself is robust against power loss and does not depend on a subsystem that may be hung.

Test failure paths

  • Block a worker and confirm the supervisor detects missing progress.
  • Disable a communication peer and verify timeout handling.
  • Inject a deliberately missed deadline in a safe test environment.
  • Confirm reset cause and post-reset diagnostics are captured.
  • Check that recovery does not repeatedly reboot without preserving useful evidence.

For safety-critical systems, watchdog behavior should be part of the system safety and fault-management design, not added as an isolated timer feature.

Final takeaway

Low-level engineering is about understanding the contract between hardware, firmware, and the operating system. Start with the specification, form a testable hypothesis, collect evidence, and validate behavior on the target platform.
