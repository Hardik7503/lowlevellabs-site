Calling Conventions and Stack Frames: AArch64 vs x86-64

A calling convention is the contract that lets separately compiled functions call each other. Knowing it lets you read crash dumps, write assembly that links with C, and understand what the compiler generated.

What the contract covers

An ABI's procedure-call standard answers a fixed set of questions. Every call in your program depends on both sides answering them the same way.

  • Where do arguments go: registers or stack, and in which order?
  • Where does the return value come back?
  • Which registers may a function overwrite freely (caller-saved), and which must it restore before returning (callee-saved)?
  • How must the stack pointer be aligned, and where is the return address?

We compare the two you are most likely to meet: AAPCS64 for 64-bit Arm (Linux, Android, most RTOSes on Cortex-A) and the System V AMD64 ABI used by Linux, BSD and macOS on x86-64. Windows x64 uses a different convention, noted at the end.

A leaf function

A leaf calls nothing, so neither architecture needs a stack frame. Compile with gcc -O2 -S or paste into Compiler Explorer:

long mac(long acc, long a, long b) { return acc + a * b; }
// AArch64: args in x0, x1, x2; result in x0
mac:
    madd    x0, x1, x2, x0      // x0 = x1 * x2 + x0
    ret                         // branch to x30
; x86-64 SysV: args in rdi, rsi, rdx; result in rax
mac:
    imul    rsi, rdx            ; rsi = a * b
    lea     rax, [rsi + rdi]    ; rax = a*b + acc
    ret                         ; pop return address into rip

The difference in return mechanism is the first thing to internalise. On Arm, bl puts the return address in a register, so a leaf never touches memory. On x86, call always pushes it onto the stack.

A non-leaf function and its frame

long scale_sum(long *v, long n, long k)
{
    long s = sum(v, n);   /* a call: must preserve k across it */
    return s * k;
}
scale_sum:
    stp     x29, x30, [sp, #-32]!   // push FP and LR, allocate 32 bytes
    mov     x29, sp                 // new frame pointer
    str     x19, [sp, #16]          // save callee-saved x19
    mov     x19, x2                 // keep k in x19 across the call
    bl      sum                     // x0 = sum(v, n); clobbers x30
    mul     x0, x0, x19
    ldr     x19, [sp, #16]
    ldp     x29, x30, [sp], #32     // restore FP, LR, free frame
    ret
scale_sum:
    push    rbx                     ; save callee-saved rbx (also realigns rsp to 16)
    mov     rbx, rdx                ; keep k in rbx across the call
    call    sum                     ; rax = sum(v, n)
    imul    rax, rbx
    pop     rbx
    ret

Both compilers solve the same problem the same way: the value needed after the call goes into a callee-saved register, which the function itself must save first. The AArch64 version must also save x30, because bl sum overwrites it.

Stack alignment, and why it crashes things

Both ABIs require 16-byte alignment, but they check it differently:

  • AArch64 can enforce it in hardware: with stack alignment checking enabled, as it normally is, a load or store using a misaligned sp as the base raises an alignment fault. That is why stp ... [sp, #-16]! always moves in multiples of 16, even to save one register.
  • x86-64 requires rsp to be 16-byte aligned at the call instruction, so on entry rsp + 8 is aligned. Nothing traps immediately; instead, SSE instructions such as movaps deep inside a library fault later. A function that calls printf from hand-written assembly after a single push works, and after two pushes crashes.

Reading a crash with this knowledge

  • On AArch64, if pc is garbage but x30 is sane, you probably returned through a corrupted saved LR: a stack buffer overflow in the function you just left. Walk frames by following x29: each frame stores the previous x29 and the saved x30.
  • On x86-64, a smashed return address shows up as a ret to an address that looks like your data, often ASCII bytes such as 0x4141414141414141.
  • Arguments live in registers that the callee is free to overwrite, so in an optimized build the debugger's "value optimized out" is honest: the argument register was reused.

Calling C from assembly

    .global start_app
start_app:                       // void start_app(void) { log_value(42); }
    stp     x29, x30, [sp, #-16]!
    mov     x29, sp
    mov     x0, #42              // first argument
    bl      log_value
    ldp     x29, x30, [sp], #16
    ret
    global start_app
start_app:
    sub     rsp, 8               ; entry rsp is 8 mod 16, realign to 16
    mov     edi, 42              ; first argument (writing edi zero-extends rdi)
    call    log_value
    add     rsp, 8
    ret
Windows x64 is different

Microsoft's x64 convention passes the first four arguments in rcx, rdx, r8, r9, treats rsi and rdi as callee-saved, requires the caller to reserve 32 bytes of "shadow space" above the return address, and has no red zone. Code that moves between Linux and Windows on x86-64 must account for this.

Key takeaway

Learn the table, then read compiler output until the patterns are familiar: arguments in, callee-saved registers for values that live across calls, a frame only when needed, and 16-byte stack alignment everywhere.
